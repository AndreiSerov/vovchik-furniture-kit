# vovchik-furniture-kit

Моделирование мебели на заказ для мебельщика: генерация 3D-модели, план раскроя, расчёт стоимости материалов.

## Состав

- `engine/kitchen/` — движок и CLI `kitchen`; `workshop/` — данные мастерской (моки); `PROGRESS.md`, `DECISIONS.md`, `MOCKS.md`.
- `skills/kitchen-brief/` — скилл Claude: разбор переписки с клиентом кухни или интервью, бриф к замеру, противоречия и вопросы клиенту. Пороги и цены салона — в `references/settings.json`.

## Установка

Нужны `git`, `python3` 3.11+, `uv` и Claude Code; агенты также пользуются `rg`, `sd` и `ast-grep` (`scripts/doctor` скажет, чего нет):

```sh
brew install git uv ripgrep sd ast-grep gh
```

```sh
uv tool install -e .    # команда kitchen в системе
export KITCHEN_HOME=/путь/к/папке/с/workshop   # не нужно внутри репозитория
kitchen check-workshop  # сводка по данным мастерской (повторный ключ, повторный id, число вне диапазона, не UTF-8 — ошибка); --json для агентов
```

В режиме `--json` ошибки идут в stderr, а stdout остаётся пустым.

`KITCHEN_HOME` — папка, где лежит `workshop/`. Без неё `kitchen` ищет корень репозитория вверх от текущей папки. Пока в `workshop/` моки, любой вывод помечен «МОК-ДАННЫЕ — НЕ ДЛЯ КЛИЕНТА»; что заменить — в `MOCKS.md`.

## Заказы

Заказы, версии проекта и журнал лежат в SQLite `$KITCHEN_HOME/orders/kitchen.db` (другой путь — `KITCHEN_DB`); папка `orders/` не в git. Заказ находится по номеру (`2026-047`), `номер-фамилия` или части фамилии, кириллицей или латиницей.

```sh
kitchen order new 2026-047-petrov --client "Петров П. П." --phone ... --address ...
kitchen order show petrov                # найти заказ, показать карточку
kitchen import petrov project.json       # новая версия, только если проект изменился
kitchen export petrov [--version N] [--out файл]   # project.json с номером версии
kitchen diff petrov v1 v2               # изменения модулей между версиями
kitchen log petrov --kind done|decision|next|note "текст"
kitchen status petrov                    # печатает и пишет orders/<заказ>/status.md (руками не править)
```

Раздел «Устарело» в `status.md` (и поле `stale` в `status --json`) перечисляет выводы, посчитанные из версии проекта старше текущей: вид, файл, версия-источник и команда пересчёта (`kitchen cut`, `edges`, `drilling`, `purchase`, `estimate`; `assembly`; `3d` — виды кухни; `production` обновляет все документы цеха: раскрой, кромление, закупку, сборочный лист и чек-лист выезда (`trip`); карта присадки — командой `drilling`). Смена данных мастерской вывод устаревшим не делает.

До этапа 1 импорт проверяет только обёртку: JSON-объект с полем `order`. Поле `version` в файле игнорируется.

## Бриф и быстрая вилка

```sh
kitchen brief save 2026-047-petrov brief.json   # проверить check_brief.py и сохранить; заказа нет — завести
kitchen brief save Петров brief.json            # одна фамилия: новый заказ со следующим номером года (ГГГГ-NNN)
kitchen brief show petrov                       # напечатать сохранённый бриф (JSON)
kitchen quick-estimate --meters 4.6             # вилка цены по pricing.yaml, с округлением и плашкой мока
```

Бриф с неизвестным полем или ошибкой схемы не сохраняется. Противоречия и пустые обязательные поля — обычное содержимое брифа: они сохраняются вместе с результатом проверки, команда печатает их число. Повторное сохранение заменяет текущий бриф (прежние остаются в БД). Одна фамилия заводит заказ, только если заказа с такой фамилией ещё нет; иначе ошибка со списком и подсказкой номера для нового. Чтобы обновить бриф существующего, указывайте номер или `номер-фамилия`. Округление берётся из `округление_цены` в `pricing.yaml` (`вверх до N` или `вниз до N`).

## Детали проекта

```sh
kitchen parts petrov                     # текущая версия проекта заказа (номер, номер-фамилия или фамилия)
kitchen parts --project project.json    # файл проекта без БД (черновик до импорта)
kitchen parts petrov --json             # тот же результат API целиком
kitchen check petrov                     # проверки проекта без расчёта выводов (или --project project.json, --json)
```

Вывод `parts` несёт версию-источник (заказ и версия или файл и хеш), бриф, с которым прошли проверки, находки проверок, фасады по цветам и общие позиции кухни (цоколь, шина, навесы, LED с блоком питания, столешница). Для заказа расчёт идёт с последним брифом; если бриф новее записанного у версии, команда предупреждает. Находки с `error` команда только показывает (это просмотр, а не импорт). Пример заказа Петрова — `tests/fixtures/petrov_project.json`.

Расчёт поддерживает нижние шаблоны `base_door`, `base_sink`, `base_bottle`, `base_drawers` (три ящика) `dishwasher_panel`, а также верхние `wall_door`, `wall_lift`, `wall_hood`, `wall_dryer`, `base_corner`, `wall_corner`, `tall_oven`. Формулы и правила конструкции — в `workshop/construction.yaml`. Ручные эталоны находятся в `tests/golden/`; добавленные правила помечены как мок и требуют проверки мастера.

`kitchen import` проверяет проект (`kitchen.checks`): сумма ряда с угловыми смещениями и пеналом против длины стены, глубина ящика и направляющая, ниша и техника, детали в рабочем поле листа, модуль без задней стенки. Техника сверяется с последним брифом заказа из БД (`check_project(path)` тоже читает бриф заказа из БД, а не из файла), версия проекта хранит id этого брифа. Ошибка отклоняет импорт, предупреждение пишется в журнал; все находки приходят сразу, каждая со значением и пределом.

## Раскрой

```sh
kitchen cut petrov                      # раскрой текущей версии + PDF orders/<заказ>/out/cutting-map.pdf
kitchen cut --project project.json     # файл проекта без БД (PDF не пишется)
kitchen cut petrov --json               # тот же результат API целиком
```

Детали листовых материалов укладываются на листы гильотинно (`rectpack`) с пропилом и обрезкой из `workshop/equipment.yaml`; текстурные материалы не поворачиваются. На каждый лист выдаются детали с координатами, порядок резов, использование листа и итог по материалу. Фасады в раскрой не идут, столешница считается общей длиной нижних модулей и целыми листами. Дробный пропил (3.2 мм — обычный диск) учитывается вверх до целого миллиметра, результат раскроя предупреждает об этом; обрезка, длина реза и размеры листа — только целые. Рез длиннее `макс_длина_реза` или деталь больше рабочего поля — ошибка. Вывод несёт версию-источник.

Для заказа `kitchen cut` ещё пишет PDF карты раскроя: страница на лист (схема в масштабе, детали с маркировкой и размерами, номера резов, списки деталей и резов, использование). Все PDF мастерской делает общий слой `kitchen.pdf`: шрифт DejaVu из пакета (`engine/kitchen/fonts/`, кириллица без системных шрифтов), водяной знак и пометка «МОК-ДАННЫЕ — НЕ ДЛЯ КЛИЕНТА» на каждой странице, пока мастерская мок, колонтитул с заказом, версией проекта, датой и номером страницы. Файл регистрируется в БД с версией-источником (`api.list_outputs`).

## Кромление

```sh
kitchen edges petrov                   # PDF orders/<заказ>/out/edging-map.pdf и регистрация в БД
kitchen edges petrov --json            # детали, стороны, метраж и путь к PDF в JSON
kitchen edges --project project.json   # черновик из файла без PDF и записи в БД
```

Карта перечисляет только детали с кромкой, их размеры и тип кромки на сторонах L1, L2, W1 и W2; в конце — метраж каждого типа: чистый, с припуском и к закупке. Метраж берётся из того же расчёта, что и `kitchen parts`. При повторном расчёте PDF и запись вывода заменяются. Если во время расчёта изменилась версия проекта, команда просит повторить расчёт.

## Присадка

```sh
kitchen drilling petrov                   # PDF orders/<заказ>/out/drilling-map.pdf и регистрация в БД
kitchen drilling petrov --json            # детали с отверстиями, сверка и путь к PDF в JSON
kitchen drilling --project project.json   # черновик из файла без PDF и записи в БД
```

Отверстия ставит тот же расчёт, что `kitchen parts` (поле `holes` детали): под конфирматы — сквозное в пласти боковины и в торце парной детали на одной оси, под чашки петель на фасадах и ответные планки на боковине со стороны петель, ряды под полкодержатели на обеих боковинах (спереди и сзади по 5 отверстий с шагом 32, центр отверстия под полку — на радиус штыря ниже полки; у дна или крыши ряд сдвигается на целые шаги, и карта называет отверстие «под полку») и отверстия направляющих Tandembox на высоте каждого ящика (`присадка.полкодержатель` и `присадка.направляющая`, МОК). Сверка сравнивает и их: отверстий полкодержателей = полкодержателей × отверстий в ряду, направляющих = комплектов × отверстий на комплект. Ряд из трёх и больше одинаковых отверстий таблица карты пишет одной строкой («15–19. полкодержатель … 1633.5…1761.5 шаг 32»). Число конфирматов и петель считается из тех же соединений и дверей шаблона, поэтому сверка «отверстий = фурнитуры» сходится; расхождение — ошибка. Координаты — от двух базовых кромок детали (правило `присадка.базовые_кромки` в `construction.yaml`, МОК). Подъёмник, навесы, ручки и опоры в карту не входят. Карта: 2–4 схемы деталей на страницу, контур в масштабе, базовые кромки выделены, у каждой схемы — с какой стороны она нарисована и с какой грани сверлить, цепочки размеров и таблица отверстий; детали без отверстий не печатаются. Вид на печати проверяет мастер (`manual`).

## Сборочный лист

```sh
kitchen assembly petrov                   # PDF orders/<заказ>/out/assembly.pdf и регистрация в БД
kitchen assembly petrov --json            # модули: детали, фурнитура «цех», шаги; путь к PDF
kitchen assembly --project project.json   # черновик из файла без PDF и записи в БД
kitchen trip petrov                       # чек-лист выезда: PDF orders/<заказ>/out/trip-checklist.pdf и регистрация в БД
kitchen trip petrov --json                # шапка из брифа и разделы чек-листа
kitchen trip --project project.json       # черновик из файла (шапка из «—»), без PDF и записи в БД
kitchen 3d petrov                         # виды кухни: PDF orders/<заказ>/out/kitchen-views.pdf и регистрация в БД
kitchen 3d petrov --json                  # сцена видов, находки проверок и расстановки, путь к PDF
kitchen 3d --project project.json         # черновик из файла без PDF и записи в БД
```

Виды кухни — A4 альбомная: страница 1 «План сверху» (стены с длинами, нижние модули сплошной линией, верхние пунктиром, глубины рядов, угловые смещения, пустые места штриховкой), дальше по странице на стену «Стена A, 2800 мм — вид спереди» (модули обоих рядов и пенал, фасады из деталей-фасадов в цвете по таблице RAL Classic, нераспознанный цвет — серый с подписью, техника, глухая часть углового модуля, цепочки ширин рядов, длина стены, высоты от пола). Масштаб подбирается под лист. Проект с ошибками проверок рисуется с плашкой «Проверки: N ошибок — сверьте проект»; ошибки расстановки — отказ без файла. Открытие на телефоне проверяет мастер (`manual`).

Лист идёт по модулям в порядке стен и рядов. У каждого модуля: таблица деталей («маркировка · имя · размер · материал»), фурнитура «цех» с количеством, техника из проекта и нумерованные шаги сборки. Шаги собираются из соединений, дверей, полок и ящиков модуля и из фурнитуры (число конфирматов в шагах равно числу конфирматов модуля); порядок этапов — ключ `сборка` в `construction.yaml` (МОК: корпус, задняя стенка, полки, ящики, фасады, ручки, опоры). Где позиция ставится, говорит ключ `ставится` в `hardware.yaml`: `цех` (по умолчанию) идёт в сборочный лист, `объект` (МОК: опоры, ручки, навесы) — в чек-лист выезда. Модуль без корпуса (фасад посудомойки) — одна строка «корпуса нет». Модуль не разрывается между страницами; длинный продолжается с заголовком «П1, продолжение». Мок — водяной знак и плашка. Вид на печати проверяет мастер (`manual`).

## Закупка и производство

```sh
kitchen purchase petrov               # purchase.md и purchase.json в orders/<заказ>/out/
kitchen purchase petrov --json        # те же позиции и суммы в JSON
kitchen production petrov             # документы цеха текущей версии: раскрой, кромление, закупка, сборочный лист
kitchen production petrov --json      # тот же результат API в JSON
```

Закупка сгруппирована по магазинам: целые листы и столешница, кромка с минимумом продажи, фурнитура упаковками, фасады по материалам и цветам со сроком. Для фурнитуры указано необходимое число изделий и число упаковок. Цены позиции и суммы по магазинам даны в рублях. Если данные мастерской — моки, каждый файл закупки содержит предупреждение. `production` считает весь комплект из одной версии проекта и регистрирует пять файлов вместе (раскрой, кромка, две закупки, сборочный лист); при ошибке сохранения восстанавливает прежний комплект.

## Смета

```sh
kitchen estimate petrov                  # estimate.md и estimate.json в orders/<заказ>/out/
kitchen estimate petrov --json           # та же смета в JSON
kitchen estimate --project project.json # смета черновика из файла, файлы не пишутся
kitchen estimate petrov --economy        # + вариант «экономия»: замены из economy.yaml и разница в цене
```

Смета берёт себестоимость материалов из закупки (тот же расчёт, что `kitchen purchase`), считает труд по операциям из `labor.yaml` — распил, кромка, присадка, сборка корпусов, ящики, монтаж, врезки, выезд, замер, проектирование — с количеством, минутами и рублями, и складывает цену: материалы, наценка, расходники, доставка и труд, итог округляется по `округление_цены` из `pricing.yaml`. Файлы привязаны к версии проекта и заменяются при повторном расчёте. Если данные мастерской — моки, смета несёт предупреждение «МОК-ДАННЫЕ — НЕ ДЛЯ КЛИЕНТА».

`--economy` добавляет вариант «экономия» (раздел «Экономия» в `estimate.md`, ключ `economy` в `estimate.json` и `--json`). Правила замен лежат в `workshop/economy.yaml` (мок): карусель → полка, Tandembox → двери с полкой, подъёмник → распашная дверь, без ведра, без сушки. Движок применяет каждую замену ко всем подходящим модулям копии текущей версии проекта и пересчитывает детали, раскрой, закупку и смету тем же путём, что обычную смету; версия проекта и таблица версий не меняются. Для каждой замены показаны модули, цена с одной этой заменой, разница с ценой «как в проекте» и текст для клиента; итог — цена со всеми предложенными заменами. Сумма разниц по строкам может не совпасть с итогом (целые листы, округление). Замена, которая не удешевляет, не предлагается (в смете — строка с причиной); модуль, на котором замена не строится, остаётся как в проекте, про него — сообщение.

## КП

```sh
kitchen quote petrov --days 35           # quote.pdf и quote.json в orders/<заказ>/out/
kitchen quote petrov --days 35 --economy # + вариант «экономия»: две цены, разница, список замен
kitchen quote petrov --days 35 --json    # та же модель КП в JSON
kitchen quote --project project.json --days 35 # КП черновика из файла, файлы не пишутся
```

КП — документ клиенту: реквизиты мастера из `workshop/master.yaml` (мок), состав кухни по модулям словами («Н1 — нижний модуль с тремя ящиками, 600 мм»), корпус, цвета фасадов, столешница, итог, предоплата по `предоплата` из `pricing.yaml`, остаток, срок и срок действия предложения. Итог — цена `kitchen estimate` той же версии проекта. Себестоимости, наценки, труда и сумм по строкам в КП нет. Срок изготовления и монтажа вписывает мастер: `--days N` (целое число рабочих дней от 1 до 365, обязательно), движок его не считает. `--economy` добавляет цену «как в проекте», цену «экономии», разницу и тексты замен для клиента. Файлы привязаны к версии проекта: после новой версии они попадают в раздел «Устарело» в `status.md` с командой пересчёта. Если данные мастерской — моки, PDF несёт водяной знак и плашку «МОК-ДАННЫЕ — НЕ ДЛЯ КЛИЕНТА».

## Разработка

```sh
uv sync                 # зависимости для разработки
scripts/sync-skills     # скиллы агента из .claude/skills.toml
scripts/check           # ruff + pytest + проверки скиллов
```

`scripts/link-skills` ставит симлинки `skills/kitchen-*` в `.claude/skills/`, `.agents/skills/`, `.qwen/skills/` (его же вызывает `sync-skills`); для Hermes один раз вручную: `scripts/link-skills --hermes` (пишет в `~/.hermes/skills/`). Запускать из основной копии репозитория, не из worktree: после удаления worktree ссылки повиснут.

`scripts/check` проверяет и скиллы `skills/kitchen-*` (`python -m kitchen.skill_lint`, тесты — `tests/test_skill_checks.py`): frontmatter только с `name` и `description`, команды `kitchen …` из кода в `SKILL.md` существуют в CLI, в теле нет формул и размеров, набор фраз `skills/triggers.json` корректен. Новый скилл добавляет в набор хотя бы одну фразу.

Проверка брифа вручную:

```sh
python3 skills/kitchen-brief/scripts/check_brief.py brief.json
```

Схема файла проекта — `engine/kitchen/schemas/project.schema.json` (`template` — перечень шаблонов, габариты больше нуля, `shelves` не меньше нуля). Пустое место ряда — запись `modules` вида `{"label": "ПМ1", "gap": true, "width": 600}` (опционально `under_countertop`): в сумме ряда есть, в цоколе, шине и LED нет. Повтор метки модуля, неизвестный шаблон и модуль, у которого при заданных габаритах деталь получается нулевого или отрицательного размера, — ошибки проверок. Импорт проверяет её;
номер `version` из файла игнорируется, при экспорте его ставит движок. Пенал задаётся
один раз в ряду своей стены. Для ряда и модуля можно указать `materials` с полями
`body`, `facades`, `handles`, `countertop`: значения модуля перекрывают ряд, ряд — проект.
Наполнение (`contents`), параметры угла и флаг `without_back` сохраняются при импорте;
расчёт `base_door` пока явно отказывает при таких параметрах. Для `base_sink` можно указать `without_back` и `contents.inserts`, для `base_bottle` — `contents.inserts`, для `base_drawers` — `contents.drawers: 3`. Модулю с одной дверью на петлях можно указать сторону петель `contents.hinge_side: "left"` или `"right"` (по умолчанию слева; у угловых сторона следует из места в ряду). Несовместимые параметры отклоняются.

Верхний модуль вытяжки использует нишу из `workshop/appliances.yaml`; вырез представляет открытый сзади проём с передней планкой. Условные размеры техники и правила требуют сверки мастером. Размер сушки задан в `construction.yaml`.
