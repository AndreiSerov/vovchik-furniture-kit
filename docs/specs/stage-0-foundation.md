# Этап 0. Основа

Статус: `ready-for-agent`
Источник: `00-source-brief.md`, этап 0; ADR 0001–0004.

## Problem Statement

Мастер хочет, чтобы ИИ-агент (Claude, GPT в Hermes, Codex, Qwen) помогал ему вести кухни на заказ, но у агента нет ни данных мастерской, ни движка, ни места, где хранятся заказы. Пока нечего вызывать, нечего проверять и некуда сохранять клиента. Любая цифра, которую агент назовёт, будет выдумана. Мастер не видит, какие данные ещё заглушки, а какие уже его.

## Solution

Репозиторий становится «мастерской»:
- данные мастера в YAML с явной пометкой мока и списком того, что заменить;
- установленная в систему команда `kitchen`, которая загружает и проверяет эти данные и печатает сводку с предупреждением о моке;
- SQLite-хранилище заказов: бриф, версии проекта, журнал;
- правила работы агента в `AGENTS.md` и трекер задач `PROGRESS.md`;
- скрипт, который делает скиллы видимыми для разных агентов.

## User Stories

1. Как мастер, я хочу один раз установить `kitchen` и вызывать его из любой папки, чтобы агент в Hermes или боте работал с моей мастерской, не находясь в репо.
2. Как мастер, я хочу указать папку мастерской через `KITCHEN_HOME`, чтобы держать данные там, где мне удобно.
3. Как мастер, я хочу, чтобы `kitchen`, запущенный внутри репо без `KITCHEN_HOME`, сам нашёл корень, чтобы не настраивать ничего при разработке.
4. Как мастер, я хочу понятную ошибку по-русски, если мастерская не найдена, чтобы знать, что исправить.
5. Как мастер, я хочу, чтобы мок-файлы содержали ровно значения из ТЗ, чтобы эталонные расчёты сходились.
6. Как мастер, я хочу, чтобы каждое добавленное сверх ТЗ значение было помечено `# ДОБАВЛЕНО (МОК)` и попало в MOCKS.md, чтобы я знал, что проверить.
7. Как мастер, я хочу MOCKS.md со списком каждого значения-заглушки по файлам, чтобы заменить их своими.
8. Как мастер, я хочу `kitchen check-workshop`, который печатает сводку: сколько материалов, кромок, фурнитуры, норм труда, какие файлы мок, чтобы быстро проверить данные.
9. Как мастер, я хочу, чтобы ошибка в YAML (опечатка в ключе, строка вместо числа, ссылка на несуществующий материал) называла файл, ключ, значение и что ожидалось, чтобы поправить без программиста.
10. Как мастер, я хочу заметную плашку «МОК-ДАННЫЕ — НЕ ДЛЯ КЛИЕНТА» в любом выводе, пока хоть один файл мастерской — мок, чтобы случайно не отправить клиенту выдуманные цены.
11. Как агент, я хочу `--json` у каждой команды с полем `mock`, чтобы не разбирать текст.
12. Как агент, я хочу, чтобы в `--json` были ровно те данные, что вернул API, чтобы текст и JSON не расходились.
13. Как мастер, я хочу заводить заказ с номером вида `2026-047` и фамилией клиента, чтобы находить его по фамилии.
14. Как мастер, я хочу, чтобы данные клиентов не попадали в git, чтобы репо можно было показать кому угодно.
15. Как агент, я хочу `kitchen import <заказ> project.json`, который проверяет проект и создаёт новую версию, только если проект изменился, чтобы версии не плодились.
16. Как агент, я хочу, чтобы импорт неверного проекта отклонялся с понятным сообщением и не портил текущую версию.
17. Как агент, я хочу `kitchen export <заказ>`, чтобы получить текущую версию проекта как файл для правки.
18. Как мастер, я хочу `kitchen diff <заказ> <v1> <v2>` по-человечески («Н2: ширина 400 → 450»), чтобы видеть, что поменялось.
19. Как агент, я хочу `kitchen log <заказ>` с типом записи (сделано, решение клиента, дальше) и текстом, чтобы вести историю заказа.
20. Как агент, я хочу `kitchen status <заказ>`, который печатает и сохраняет `status.md`: этап, версия проекта, решения клиента, сделано с датами, дальше, чтобы новая сессия знала, где остановились.
21. Как агент, я хочу находить заказ по номеру или по фамилии («петров»), а при нескольких совпадениях получать список, чтобы фраза «продолжи заказ Петрова» работала.
22. Как агент скилла `kitchen-brief`, я хочу `kitchen brief save <номер-фамилия> brief.json`, который создаёт заказ, сохраняет бриф и первую запись журнала.
23. Как агент, я хочу `kitchen quick-estimate --meters N` с вилкой из `pricing.yaml`, чтобы назвать клиенту ориентир без счёта в голове.
24. Как мастер, я хочу `scripts/link-skills`, который делает скиллы из `skills/` видимыми для Claude Code, Codex и Qwen, и `--hermes` для Hermes.
25. Как агент в новой сессии, я хочу прочитать правила из `AGENTS.md`, PROGRESS.md и DECISIONS.md, чтобы продолжить с первой незакрытой задачи.
26. Как мастер, я хочу DECISIONS.md, где каждое спорное правило помечено «ПРОВЕРИТЬ МАСТЕРУ», чтобы разобрать их разом.

## Implementation Decisions

### 0.1 — Каркас, правила, трекер
- Пакет `kitchen` в папке `engine/`; `pyproject` становится устанавливаемым пакетом с консольной командой `kitchen` и зависимостями `pydantic`, `pyyaml`, `typer`, `rectpack`, `reportlab`; в dev — `pypdf`.
- CLI на `typer`.
- `AGENTS.md` получает раздел с принципами из ТЗ в редакции грилинга (принцип 3 — по ADR 0001), картой «что где лежит» и таблицей «какой скилл когда». `CLAUDE.md` остаётся `@AGENTS.md`.
- `PROGRESS.md` — чек-лист всех тикетов всех этапов со ссылками на спеки. `DECISIONS.md` и `MOCKS.md` создаются.
- `.gitignore`: `orders/*` (БД и папки заказов), `orders/*/out/`.
- README: установка (`uv tool install -e .`), `KITCHEN_HOME`, ссылка на скрипты; сборка zip для claude.ai удаляется (ADR 0003).
- `scripts/link-skills` (ADR 0003): симлинки `skills/kitchen-*` в `.claude/skills/`, `.agents/skills/`, `.qwen/skills/`; `--hermes` — в `~/.hermes/skills/` (ручной шаг). Идемпотентен, не трогает чужие скиллы. `scripts/sync-skills` вызывает его в конце; `scripts/doctor` сообщает о битых ссылках.

### 0.2 — Мок-файлы и MOCKS.md
Зависит от: 0.1
- Шесть файлов `workshop/` ровно со значениями ТЗ. Единственное отличие: в `hardware.yaml` список под ключом `позиции:`, потому что YAML не допускает ключ и список на одном уровне.
- Политика добавления: новые ключи разрешены, каждый с комментарием `# ДОБАВЛЕНО (МОК)` и строкой в MOCKS.md. Новые по смыслу данные — в новых файлах с `mock: true`: `appliances.yaml` (типовые габариты и минимальные ниши: духовка, СВЧ, ПММ 45, вытяжка 60, индукция 60, мойка), `economy.yaml` (этап 3), `master.yaml` (реквизиты для КП, этап 3).
- MOCKS.md: по файлам, каждое значение-заглушка, где оно влияет (какие выводы), чем его заменить.

### 0.3 — Загрузчик мастерской и `check-workshop`
Зависит от: 0.2
- `kitchen.api.load_workshop(home)` → модель мастерской. Русские ключи YAML — pydantic-алиасы английских полей (`GLOSSARY.md`). Ошибки валидации переводятся в русские сообщения: файл, путь ключа, значение, ожидание.
- Перекрёстные ссылки проверяются: материал задней стенки, материал ящика Tandembox — существующие `id`.
- Строковые формулы из `construction.yaml` (`"H - 4"`, `"(W - 4 - 2) / 2"`) разбираются безопасным вычислителем выражений над именованными переменными (`W`, `H`, `D`, `внутр_ширина`); `eval` не используется. Нераспознанная формула — ошибка загрузки.
- Таблицы ступеней (`петли_по_высоте_фасада`, `конфирматы_по_длине_соединения`) — общий тип «первая ступень, где значение ≤ порога».
- Модель знает, какие файлы мок (`mock_files`), и флаг `is_mock`.
- Общий для всех выводов механизм пометки мока: результаты API несут `mock: bool` и `mock_files`; CLI печатает плашку первой и последней строкой; `--json` содержит те же поля.
- `kitchen check-workshop`: сводка по каждому файлу и предупреждение о моке; код выхода 0 при валидных данных (мок — не ошибка), 1 при ошибках.

### 0.4 — Хранилище заказов
Зависит от: 0.3
- SQLite по ADR 0001. Путь: `KITCHEN_DB`, иначе `$KITCHEN_HOME/orders/kitchen.db`. Схема создаётся при первом обращении; номер схемы хранится в БД для будущих миграций.
- Таблицы по смыслу: заказы (номер `ГГГГ-NNN`, slug фамилии, клиент, контакты, адрес, даты), бриф, версии проекта (номер, JSON, время, хеш содержимого), журнал (время, тип: `done` / `decision` / `next` / `note`, текст, версия проекта на момент записи), выводы (вид, путь, версия-источник, время) — таблица выводов используется с этапа 2.
- Импорт: валидация схемы проекта (этап 1.1 даёт полную схему; до него — минимальная обёртка с номером заказа) → сравнение хеша с текущей версией → новая версия или «без изменений». Номер версии в файле игнорируется и ставится движком.
- Экспорт пишет `project.json` с полем версии.
- `diff` сравнивает две версии по модулям и полям и печатает изменения по-русски.
- `status` собирает `status.md` в `orders/<заказ>/` из журнала и последней версии: этап, версия проекта, решения клиента, сделано (с датами), дальше. Файл генерируется, руками не правится, в шапке это сказано.
- Поиск заказа: точный номер, `номер-фамилия` или подстрока фамилии (латиница и кириллица); при нескольких совпадениях — ошибка со списком.

### 0.5 — Бриф в хранилище и быстрая вилка
Зависит от: 0.4
- `kitchen brief save <номер-фамилия> <brief.json>`: проверяет бриф существующим `check_brief.py` (без внешних зависимостей, вызывается как модуль), создаёт заказ, если его нет, сохраняет бриф, пишет запись журнала «бриф сохранён».
- Номер заказа задаёт мастер; если передана только фамилия, движок выдаёт следующий свободный номер текущего года.
- `kitchen quick-estimate --meters N`: вилка `быстрая_оценка_за_пог_м × N` с округлением из `pricing.yaml`, с пометкой мока.

## Testing Decisions

- Хороший тест проверяет внешнее поведение через `kitchen.api` на временном `KITCHEN_HOME` (копия `workshop/` и пустая БД в `tmp_path`), а не внутренние функции загрузчика.
- Загрузчик: валидные мок-файлы грузятся, `is_mock` истинен, `mock_files` содержит все шесть; испорченные копии (опечатка ключа, строка вместо числа, битая ссылка на материал, неизвестная формула) дают ошибку с файлом, ключом и значением.
- Вычислитель формул: значения формул фасадов для W=600, H=720 совпадают с эталоном (716, 596, 297); запрещённые конструкции отклоняются.
- Хранилище: импорт создаёт v1; повторный импорт того же — «без изменений»; изменённый — v2; неверный проект отклоняется, текущая версия не меняется; экспорт → импорт без правок не создаёт версию; diff показывает изменённое поле; журнал и `status.md` содержат все разделы; поиск по фамилии и неоднозначный поиск.
- `brief save` на брифе из тестов `check_brief.py` создаёт заказ и запись журнала.
- CLI — контрактные тесты: коды выхода, `--json` равен результату API, плашка мока первой и последней строкой, `KITCHEN_HOME` и поиск корня, русская ошибка «мастерская не найдена».
- `scripts/link-skills` проверяется тестом во временной папке: создаёт ссылки, повторный запуск ничего не ломает, чужие файлы не трогает. Вариант `--hermes` — `manual`.
- Прецедент — `tests/test_check_brief.py`.

## Out of Scope

- Схема проекта целиком (этап 1.1); здесь только версии как непрозрачный проверяемый JSON.
- Учёт выводов и устаревшие расчёты (этапы 2 и 5.3).
- Изменение самого скилла `kitchen-brief` (этап 6.5).
- Точечные команды правки проекта (ADR 0001).
- MCP-сервер (ADR 0002).

## Further Notes

- Решения грилинга, которые не в ADR, но нужны всем этапам: неоднозначные правила конструкции агент решает сам и пишет в DECISIONS.md с «ПРОВЕРИТЬ МАСТЕРУ»; учёт деловых остатков не делаем; шрифт для кириллицы в PDF — DejaVu в репозитории.
