# DECISIONS

Действующие решения по темам. В каждой теме только то, что верно сейчас: новое решение заменяет старое на месте, история — в git (`git log -p DECISIONS.md`). В скобках — тикет, где решение принято или последний раз изменено. Принятые архитектурные решения лежат в `docs/adr/`.

Пометка «ПРОВЕРИТЬ МАСТЕРУ» — правило, которое агент выбрал сам; оно ждёт разбора мастером. Решение мастера снимает пометку и называется «решение мастера».

Перед записью найди свою тему и проверь, не противоречит ли новое правило уже записанному. Противоречит — перепиши старую запись, а не добавляй вторую.

## Общие правила

- **Где спека и ТЗ расходятся, верна спека** (`docs/specs/stage-N-*.md` и `docs/adr/`); исходное ТЗ лежит в `docs/specs/00-source-brief.md`. (грилинг)
- **Неоднозначное правило.** Мелочь, не меняющая чисел и документов для клиента или цеха, — агент решает сам, записывает сюда с пометкой «ПРОВЕРИТЬ МАСТЕРУ» и продолжает. Правило, которое меняет размеры, количества, цены или вывод для клиента или цеха, — вопрос мастеру через координатора до реализации. (грилинг, ретро)
- **Решения агента по поручению мастера** (решение мастера 2026-11-15: «делай МВП, далее исправим»): открытые вопросы тикетов MVP агент решил сам; в тикете — блок «Решения агента (MVP…)», сборку он не держит. Сводка и что пересмотреть — `docs/reviews/2026-11-15/agent-decisions.md`. Новые вопросы, которые меняют числа или вывод для клиента или цеха, по-прежнему идут мастеру. (проверка готовности)
- **Мок клиенту не уходит** (решение мастера 2026-11-15): вывод на мок-данных агент показывает только мастеру с плашкой, в том числе вилку быстрого опроса; на «отправь всё равно» отказывает. Исключения для вилки нет. (проверка готовности этапа 6)
- **Учёт деловых остатков не делаем.** Раскрой каждого заказа считается с нуля из целых листов; обрезки прошлых заказов не учитываются. (грилинг)

## Мастерская (`workshop/`)

- **Ключи YAML остаются русскими, поля моделей английские** (`GLOSSARY.md`), связь через pydantic-алиасы. Неизвестный ключ — ошибка загрузки (ловит опечатки). (01)
- **`workshop/hardware.yaml`: список лежит под ключом `позиции:`** рядом с `mock: true`. В ТЗ ключ и список стоят на одном уровне, YAML такое не допускает. Остальные пять файлов — ровно значения ТЗ. (грилинг)
- **`KITCHEN_HOME` указывает на папку, внутри которой лежит `workshop/`**, а не на сам `workshop/`. С `KITCHEN_HOME` достаточно существующей папки `workshop/`; без него корень ищется вверх от текущей папки и требует `workshop/construction.yaml`. (01)
- **Пометка файла как мока — только `mock: true`** (строгий bool). `mock: false` снимает плашку для этого файла. (01)
- **Целые миллиметры.** Все миллиметровые поля `construction.yaml`, `materials.yaml` (толщины, размер листа и столешницы) и `equipment.yaml` (припуск кромки, обрезка по периметру, макс. длина реза) — `Int`: дробное значение (`отступ_от_боковин: 1.5`, `обрезка_по_периметру: 12.5`, лист `[2800.6, 2070]`) — ошибка загрузки, молчаливого `int()` и `round()` нет. Габариты модуля в проекте — тоже целые. Исключения — пропил (см. тему «Раскрой») и `присадка.полкодержатель.центр_ниже_полки` (до десятых мм, решение мастера, тема «Присадка»). (05, 33, 20)
- **Диапазоны чисел живут в типах моделей** (`NonNegNum`, `PosInt` в `models.py`), а не в проверках по месту использования. Цены, ставка, наценка, доля расходников, доставка, предоплата, нормы труда, запас кромки, срок — не меньше нуля; упаковка фурнитуры, шаг полок, размер листа, макс. длина реза — больше нуля; `inf` и `nan` в любом числе мастерской — ошибка. Вилка `быстрая_оценка_за_пог_м` — два положительных числа по возрастанию (равные допустимы). Сообщения по-русски с файлом и ключом, без английского хвоста pydantic. Границы стоят на каждом числовом поле всех девяти файлов: это проверяет `test_every_numeric_model_field_has_a_bound` в `tests/test_structure_guards.py` по типам моделей (поэтому ограждению разрешён `kitchen.models`) (без границы в типе — только четыре поля, которые ограничивает разбор правила или валидатор). Сетка в том же файле `tests/test_workshop_number_grid.py` ловит падения расчёта: поле × −1, 0 — ошибка загрузки либо Петров считается без отрицательных чисел, кроме положения задней стенки ХДФ). Больше нуля: толщина корпуса, высоты, глубины, `царга_ширина`, `крепёж_шаг`, высота и шаг полки, высота ножек и `порог_ширины`, пороги ширины фасадов, верхний из трёх ящиков, `макс_ширина` бутылочницы, `длина_направляющей`, `ширина_сушки`, толщины материалов, упаковка, шаг, размеры листов, габариты техники. Не меньше нуля (ноль законен): пропил, обрезка, припуск кромки, отступ по контуру задней стенки и отступы полки, зазор фасадов, все количества (полкодержатели, ножки, саморезы, навесы, `саморезов_заглушки`, значения ступенчатых таблиц и их пороги), запасы, смещения и допуск угла, `мин_глубина_планки`, цены, ставка, нормы, наценка, доли, доставка, срок. Предоплата — доля `0..1` (больше единицы дала бы отрицательный остаток). Полей без границы нет: отрицательным не может быть ни одно число мастерской. (33)
- **Загрузка YAML строгая:** повторный ключ в любом разделе — ошибка загрузки со строкой и ключом; повторный `id` в списках `hardware.yaml`, `materials.yaml` (листовые, кромка, столешницы, фасады) и `appliances.yaml` — ошибка; файл не в UTF-8 — русская ошибка с именем файла; BOM в YAML допускается (`utf-8-sig`). Merge-ключ `<<:` поддерживается (повторы проверяются только среди явных ключей раздела, подмешанные можно переопределять); нехешируемый ключ (`[1, 2]: 3`) — русская «ошибка синтаксиса YAML». Скаляр под списочным ключом называет ошибка модели (файл и ключ), сводка `check-workshop` его не считает и не падает; русские ключи сводки берутся из алиасов моделей, а не из второго списка. (33)
- **Формулы** (`"H - 4"`) проверяются при загрузке дважды: синтаксис — сразу (парсер без `eval`), имена переменных — против известного набора каждого ключа (у формул фасадов — только `H` и `W`, у ящика Tandembox — `внутр_ширина`). Неизвестная переменная или запрещённая конструкция — ошибка загрузки. Деление — только нацело: `(W - 4 - 2) / 2` при W=600 даёт 297; остаток — `OrderError` с модулем и шириной («Модуль Н1: ширина 601 — фасады «(W - 4 - 2) / 2» не делятся нацело; возьмите чётную ширину»). Дроби в мм мастер не ждёт; если понадобится — вернёмся. ПРОВЕРИТЬ МАСТЕРУ. (05)
- **Прозаические правила читаются, а не зашиты.** `заглушки`, `ответные_планки`, `ручки` разбираются при загрузке в `RatioRule` («по одной на конфирмат/петлю/фасад», «по N на …»); `кромка.корпус/царги/полки` — в `EdgeRule` («передняя видимая кромка, ПВХ 0.8», «передняя кромка» — грань `+y`; «одна длинная сторона» — сторона `L1`). Иная формулировка — ошибка загрузки с файлом, ключом и значением. (05)
- **Округления — типизированные правила.** Цена — `RoundingRule` (`up`/`down` и шаг в рублях; понимает «вверх до N» и «вниз до N», N > 0); метраж кромки — `MeterRounding` («вверх до 0.1 м»). Другая формулировка — ошибка загрузки. Деньги считаются в `Decimal` от строкового вида чисел, без шума плавающей запятой (`4.6 × 85000` не превращается в 392 000). (04, 05)
- **Ключи МОК, добавленные движком:** `construction.yaml` — `фурнитура` (id позиций hardware.yaml, чтобы id не жили в коде шаблона), `ответные_планки` (по одной на петлю), `ручки` (по одной на фасад, id — из `materials.handles` проекта), `полка.высота` (300), `полка.шаг` (300), `ножки.порог_ширины` (800), `фасады.одна_дверь_макс_ширина_модуля` (600), `фасады.две_двери_мин_ширина_модуля` (300), `техника_в_столешницу`, `общие_позиции`, `присадка` (тикет 19); `materials.yaml` — `кромка_к_материалу`, `толщина` у ХДФ (3) и фасада МДФ (19; у ЛДСП корпуса — `толщина_корпуса`). Список замен — `MOCKS.md`. (05, 10, 11, ревью этапа 1)
- **Ножки: ключи `до_800`/`свыше_800` обязаны следовать порогу `порог_ширины`.** Движок читает порог значением; если мастер поменяет порог (скажем, на 900), имена ключей надо переименовать вручную. Ключи из ТЗ не переименованы. ПРОВЕРИТЬ МАСТЕРУ. (05)
- **Нечитаемый файл мастерской считается моком, пока его не починят** (осторожное правило): файл, который не прочитался или не прошёл проверку, без явного `mock: false` в разобранном виде несёт плашку, даже если остальные файлы `mock: false`; плашка исчезает, когда данные верны. (33)
- **Мастерская не загрузилась — импорт отклоняется** с причинами из `check-workshop`: непроверенный проект версией не становится. (10)
- **Плашка мока на всех командах заказа** (`order`, `import`, `export`, `log`, `status`) показывается, пока хоть один файл мастерской мок, и на тексте ошибки команды тоже (`api.is_mock`; цифры в тексте отказа могли быть посчитаны из мока); поэтому мастерская нужна всегда (и для `KITCHEN_DB`: от неё `orders/<заказ>/`). В JSON каждой команды с результатом на `Result` — вычисляемое поле `warning` («МОК-ДАННЫЕ — НЕ ДЛЯ КЛИЕНТА» при `mock: true`, иначе `null`); у результатов со своим `mock_notice` (закупка и др.) `warning` его дублирует. (03, ревью этапа 1)
- **Уборка загрузки YAML (тикет 45).** Повтор ключа ищется при композиции узлов (`_StrictLoader.compose_mapping_node`): каждый словарь проверяется по своим ключам один раз, подмешанный `<<` словарь — отдельный узел со своей проверкой; законное перекрытие подмешанного ключа не ошибка. `пропил` строгого типа: «3.2» в кавычках — «ожидалось число». YAML с тысячами уровней вложенности — русская ошибка «слишком глубокая вложенность», а не `RecursionError`. Строгий тип пока только у `пропил` (так в тикете); у остальных чисел строка в кавычках по-прежнему принимается. (45)
- **`мин_размер_детали`** — ключ `construction.yaml` (МОК 30 мм, обязательный; строка в `MOCKS.md`): деталь, у которой длина или ширина меньше, — ошибка проверок проекта. Решение агента по поручению мастера, сверить после MVP: при 50 под ошибку попадает реальная деталь Петрова `В1-дно-выт-1` 568×40. (45)

## Заказы и БД

- **Схема БД** — в `PRAGMA user_version` (номер — `store.SCHEMA_VERSION`); БД новее движка — отказ с просьбой обновить `kitchen`. Создание и обновление схемы идут под `BEGIN IMMEDIATE` с перечитыванием `user_version` под блокировкой (параллельный первый запуск безопасен, сбой откатывается). Новая схема — запись в `store.MIGRATIONS` и `SCHEMA_VERSION`. Относительный `KITCHEN_DB` считается от `KITCHEN_HOME`. Контакты клиента — одно поле `phone`. (03)
- **Идентичность заказа:** номер `ГГГГ-NNN` уникален; slug — фамилия латиницей. Кириллица транслитерируется простой таблицей (ё→e, ж→zh, х→kh, ц→ts, ч→ch, ш→sh, щ→shch, ю→yu, я→ya, ъ/ь опускаются). (03)
- **Разбор запроса заказа — один, `store.parse_query`:** номер `ГГГГ-NNN`, полный `номер-фамилия` или фамилия (без цифр). Любой другой запрос с цифрами (`2026-47-ivanov`, `petrov 2026-047`) — ошибка «похоже на номер заказа, ожидалось ГГГГ-NNN-фамилия». Поиск: точный номер, `номер-фамилия` или подстрока slug фамилии и транслитерированного имени клиента. (03, 04)
- **Время** пишется в UTC; даты в `status.md` показываются по местному времени. (03)
- **`export` без `--out`** пишет в `orders/<заказ>/project.json`. Папка выводов `orders/<заказ>/out`, занятая файлом, — русская ошибка с путём. Запись `export` и `status.md` идёт через `api._write_text`: папка вместо файла, недоступный путь, нет прав — русская `OrderError` с путём, без трейсбека. JSON проекта и брифа читается как `utf-8-sig` (BOM Блокнота Windows допускается); файл не в UTF-8 — русская ошибка. (03, 33)
- **Этап в `status`:** есть выводы — «Выводы»; иначе есть версия проекта — «Проект»; иначе есть бриф — «Бриф»; иначе «Новый заказ». «Дальше» — пять последних записей `next`; пустые разделы пишут «Пока ничего». (03)
- **Бриф хранится строкой на каждое сохранение, актуален последний** (`brief show` берёт последнюю). Прежние строки — история. Колонка `briefs.check_result` хранит итог `check_brief.py` на момент сохранения (схема 2). (04)
- **`brief save` отклоняет только `errors` и `unknown_fields`.** Противоречия и пустые обязательные поля — обычное содержимое брифа: сохраняются, команда печатает их число. (04)
- **Какой заказ получает бриф:** номер — существующий заказ; `номер-фамилия` — существующий или новый с этим номером (чужая фамилия при занятом номере — ошибка); одна фамилия — новый заказ со следующим номером текущего года (максимум в году плюс один, 001 если пусто), но только если заказа с точно такой фамилией (slug целиком, по всем годам) нет. Если есть — ошибка со списком и подсказкой номера для нового. Имя клиента берётся из `client.name` брифа только при создании заказа. (04)

## Импорт и схема проекта

- **Схема проекта:** `contents` содержит `doors`, `shelves`, `drawers`, `inserts`, `lift`; `contents.hinge_side` — сторона петель одной двери (тикет 19); `corner` содержит только `adjacent_wall` (смещения угла — ключи `construction.yaml`, своего смещения у модуля нет); `appliances` связывает технику с модулем по `module`. Материалы и цвет фасада модуля перекрывают ряд, ряд — проект. Пенал записывается один раз. Метки модулей уникальны (находка `duplicate_label` в `kitchen.checks`: импорт и `check_project` получают её из одного места; пенал, записанный в двух рядах, — повтор). Габариты модуля и ниши больше нуля, `shelves` не меньше нуля — ограничения в типах `project.py`; `template` в JSON Schema — перечень `TEMPLATES` (подставляется при выгрузке схемы), а разбор проекта неизвестный шаблон пропускает: его называют проверки (`module_build`). ПРОВЕРИТЬ МАСТЕРУ. (06, ревью этапа 1, 34)
- **Импорт:** хеш — sha256 канонического JSON нормализованного проекта (`api._project_hash`: дамп модели `Project` без `version` и без `order`, ключи отсортированы), поэтому написание `order` (три формы), `600` и `600.0`, порядок ключей версию не создают. `order` в хеше не нужен: импорт уже сверил его с заказом. `contents: {}` и отсутствие `contents` у модуля — один проект. Версии, записанные в БД до этой правки (хеш сырого JSON), история не переписывается: при импорте хеш версии пересчитывается из её данных (`_same_project`), и тот же файл новой версии не создаёт; для проекта, которого схема не читает, хеш — сырого JSON, как раньше. Хеш источника в `parts`/`cut`/`estimate` берётся тем же способом и у файла, и у версии из БД. Входной `version` игнорируется, версию назначает движок и добавляет экспорт. Поле `order` — номер `ГГГГ-NNN` или `номер-фамилия`; фамилия сравнивается после транслитерации, чужая отклоняется. Проверка — `validate_wrapper`: `errors` отклоняют импорт, `warnings` пишутся в журнал заметками `note`, только если версия создана. (03, 06, 10)
- **`diff` сравнивает модули и пустые места по метке**, включая положение (среди всех записей ряда) и поля; пустое место: «добавлено пустое место 600 мм (A, нижний, 1)», «удалено пустое место», «ширина 600 → 650», «техника не задано → холодильник»; модуль и пустое место с одной меткой: «Н6: модуль → пустое место». Старые версии без стен, рядов и меток — понятная ошибка. (06, 32)
- **Пустое место — запись списка `modules` ряда** (решение мастера, тикет 32): `{"label": "ПМ1", "gap": true, "width": 600}`, без `template`; необязательное `under_countertop: true`. В схеме — класс `project.Gap`, запись ряда выбирается по ключу `gap`; неизвестные ключи отклоняются, ширина больше нуля. Метка общая с модулями (`duplicate_label`). Все обходы берут `Row.cabinets` (модули без пустых мест) или пропускают `Gap` явно: детали, раскрой, присадка, закупка, «экономия», монтаж сметы, сборочный лист, сторона глухой части, `corner` и `row_sum`/цоколь/шина/столешница в `common`. Само пустое место в `parts` — список `gaps` (деталей нет; в эталоны не входит), в КП — строка без цены. (32)
- **Неподдерживаемое шаблоном поле** (наполнение, которого шаблон не строит) — русская ошибка, а не молчаливый неверный расчёт. (06)

## Шаблоны модулей

- **Свойства шаблонов** (`carcass`, `drawers`, `both_rows`, `appliances`) живут в реестре `Template` (`parts.TEMPLATES`); имя детали задней стенки — константа `BACK_PANEL`. Остальной движок берёт их из реестра, а не по имени шаблона (ограждение — `tests/test_structure_guards.py`). (10, ревью этапа 1)
- **Кромка следует за гранью.** Шаблон называет грань (`+y`), `make_part` после выбора оси длины переводит её в L1/L2/W1/W2 (правило — в `GLOSSARY.md`). При W < 592 дно и полка 560-глубокого корпуса длиннее по глубине, их кромка — на `W2`. (05)
- **Площадь фасада — поле `area_m2` у детали** (длина × ширина, м², без округления: 0.212652). Площадь фасадов проекта — сумма в `Decimal`, округлённая до 4 знаков один раз (0.425304 → 0.4253). (05)
- **Положения деталей в модуле** (для 3D, угол детали — с минимальными координатами): дно на дне корпуса (z=0), царги плашмя между боковинами у верха (`z = H − толщина корпуса`), передняя у фасада, задняя у стенки, полки по `полка.высота`, ХДФ вплотную сзади корпуса (y = −толщина ХДФ, отступ по контуру внутрь), фасады спереди на высоте зазора, левый фасад — у стены A слева. ПРОВЕРИТЬ МАСТЕРУ. (05)
- **Полки и двери (`base_door`, `wall_door`)** — через `contents.shelves` и `contents.doors`; остальные шаблоны эти поля отклоняют по-русски. `contents.shelves` перекрывает старое поле модуля `shelves` (по умолчанию 1). Полки: маркировка `Н1-полка` при одной и `Н1-полка-N` при нескольких, i-я на высоте `полка.высота + (i-1) * полка.шаг`, полкодержатели `полка.полкодержателей` на каждую; больше, чем помещается под верхней деталью корпуса (`z <= H - 2T`), — ошибка с пределом; 0 полок — без детали и полкодержателей. Двери: 0 — открытый модуль, 1 и 2 — с зазорами и петлями; без `contents.doors` — правило ширины (одна при W ≤ 500), больше двух дверей модуль не строит. ПРОВЕРИТЬ МАСТЕРУ: шаг полок и пределы ширины; нужны ли три двери и неравномерные полки. (ревью этапа 1)
- **Царги `base_door`: обе у верха корпуса** — передняя и задняя; у обеих кромится длинная сторона, обращённая в комнату (`L1`). ПРОВЕРИТЬ МАСТЕРУ (в ТЗ — «сверху 2 царги», стороны не оговорены). (05)
- **Мойка:** две царги, без полки и задней стенки по МОК `мойка`; вставки из `contents.inserts`; без задней стенки — предупреждение. ПРОВЕРИТЬ МАСТЕРУ. (07)
- **Бутылочница:** одна выдвижная вставка, по умолчанию `bottle_150`; полок и петель нет, фасад один, корпус с задней стенкой. Максимальная ширина 150 мм — ключ МОК `бутылочница`. ПРОВЕРИТЬ МАСТЕРУ. (07)
- **Деталь, которой нет:** шаблон, который при данных габаритах строит деталь с размером не больше нуля, положением вне модуля (кроме задней стенки ХДФ: `y < 0`) или фурнитуру меньше нуля, даёт ошибку модуля (`parts._check_sound`, одна проверка для всех шаблонов, в проверках — находка `module_build`); `compute_parts` строит модули только через неё, отдельной проверки итога нет. Положительные, но невозможные детали (полка 540×1) и минимальная ширина ящика — данные мастерской, в список на конец этапа. (34)
- **Ящик Tandembox строит одна функция `parts.drawer_parts`** для `base_drawers` и пенала. Ящик, который не помещается в глубину корпуса или по высоте за свой фасад, — ошибка «ящик не помещается» с цифрами, один текст для обоих шаблонов. (34)
- **Три ящика Tandembox:** внутренняя ширина — ширина модуля минус две толщины корпуса, дно и задняя стенка по формулам мастерской, металлические борта в комплекте. Высота верхнего фасада — из мастерской, два остальных делят оставшуюся высоту поровну после двух межфасадных зазоров; дробный миллиметр отклоняется. Детали ящика по `ящики.кромить_детали` не кромятся (`true` — все четыре стороны). Дно выше нижнего края фасада на толщину корпуса, задняя стенка сзади дна, расположение по ширине округляется вниз до мм; размеры сверить с каталогом направляющих. ПРОВЕРИТЬ МАСТЕРУ. (07)
- **ПММ:** один фасад по формулам нижнего фасада, без корпуса и фурнитуры: крепёж по инструкции техники. ПРОВЕРИТЬ МАСТЕРУ. (07)
- **Верхние модули:** дно и крыша между боковинами, по 2 навеса и одна полка (кроме сушки и вытяжки); высота фасада по отдельной формуле мастерской. ПРОВЕРИТЬ МАСТЕРУ. (08)
- **Подъёмник:** один цельный фасад, один комплект Aventos, без петель и ответных планок; допустим также у вытяжки и сушки по `contents.lift`. ПРОВЕРИТЬ МАСТЕРУ. (08)
- **Сушка:** вставка `dryer_750` только при указанной в МОК ширине 750; вместо полки, без дна; крыша и задняя стенка сохраняются. ПРОВЕРИТЬ МАСТЕРУ. (08)
- **Вытяжка:** ниша — по `niche_*` вытяжки проекта, недостающее — из `appliances.yaml` (`parts.built_niche`); внизу открытый сзади проём на всю внутреннюю ширину, передняя планка оставшейся глубины крепится двумя соединениями к боковинам; минимум глубины планки 40 мм, иначе ошибка. Полки нет. Сверить по монтажной схеме конкретной вытяжки. ПРОВЕРИТЬ МАСТЕРУ. (08, ревью этапа 1)
- **Угловые модули:** прямой корпус с одной дверью и неподвижной заглушкой из указанного в мастерской материала. Глухая часть — со стороны угла: у последнего модуля ряда (стена А идёт слева направо, стена Б начинается от угла) справа, дверь со стороны прохода; у первого модуля ряда с соседями — зеркально, слева. Единственный в ряду считается последним. Сторона определяется по месту в ряду, отдельного ключа нет. Нижний фасад 450 мм, верхняя заглушка 150 мм; нижний без полки, с каруселью; верхний — той же глубины, что обычные верхние (решение мастера 2026-11-15, тикет 50; прежние 600 мм и ключ `глубина_верхнего` убраны), с полкой и двумя навесами. Заглушка кромится по четырём сторонам, 4 самореза. Смещение нижнего ряда соседней стены 600 мм и допуск стены 0 мм — ключи мастерской; смещение верхнего ряда считает движок: глубина верхних плюс толщина фасада углового модуля, без зазора (мок 320 + 19 = 339; ключ `смещение_верхнего` убран). Угол с двумя рядами верхних (глубина 600) — бэклог. ПРОВЕРИТЬ МАСТЕРУ. (09, ревью этапа 1, 50)

ПРОВЕРИТЬ МАСТЕРУ. (09, ревью этапа 1)

## Техника, ниши и бриф

- **Техника в пустом месте (решение мастера, тикет 32):** список видов и зазор — `construction.yaml` `пустое_место.техника` (холодильник, посудомойка, плита, стиральная машина) и `пустое_место.зазор` (20 мм), МОК, в `MOCKS.md`. Привязка — `appliances[].module = метка места`, модуль не требуется, ниша не проверяется; находки `gap_too_small` (ширина техники из брифа, иначе из проекта, плюс зазор), `gap_appliance` (другой вид), `gap_upper_appliance` (верхний ряд), `gap_built_in` (warning: холодильник в брифе встраиваемый), `gap_width` (дробная ширина, «Целые миллиметры»). Вид `fridge` добавлен в `APPLIANCE_KINDS`; холодильник брифа (`appliances.fridge`) входит в `brief.appliances()` и сверяется как прибор. Падежи названий — `parts.GAP_NAMES`. (32)
- **Несколько приборов в одном пустом месте (решение мастера 2026-11-15, тикет 32):** место не меньше суммы их ширин плюс `пустое_место.зазор`, иначе одна находка `gap_too_small` со всеми приборами в тексте («450 + 560 + зазор 20»). (32)
- **Решения исполнителя, тикет 32 (ПРОВЕРИТЬ МАСТЕРУ):** (1) `gap_built_in` — только в названном направлении (бриф «встраиваемый», в проекте в пустом месте); «или наоборот» из спеки не реализовано: у встраиваемого по проекту холодильника в модуле шаблона нет, его уже ловит `appliance_no_niche`. (2) Встраиваемый холодильник брифа без привязки в проекте даёт `appliance_no_template` (warning) по общему правилу «Состав техники». (3) В КП названия приборов одного места через «и». (4) Коды `gap_upper_appliance` и `gap_width` — выбор исполнителя; тексты — из спеки.

- **Источник размеров техники — бриф** (решение мастера: `appliances.yaml` — моки, настоящие размеры говорит клиент). Проверки при импорте и `api.check_project` читают последний бриф заказа в БД. ADR 0001 это не нарушает: бриф — входные данные заказа, источник правды о проекте — версия проекта. (10)
- **Какой бриф:** бриф, с которым проверялась версия, записан в строку версии (`project_versions.brief_id`, схема 3). Повторный импорт без изменений возвращает записанный у версии бриф. `check_project(path)` читает последний бриф заказа и называет его (`brief_id`, `brief_saved_at`). ПРОВЕРИТЬ МАСТЕРУ. (10)
- **Габариты корпуса и ниша разделены.** И в проекте, и в брифе `width/height/depth` (в брифе ещё строка `dimensions` «Ш×В×Г» старых брифов; непонятная — `warning` `brief_dimensions`) — корпус прибора, только справочно, с нишей не сравниваются. Ниша — необязательные `niche_width/niche_height/niche_depth` (в брифе — `niche_*_mm`); нет их — типовая ниша по типоразмеру из мок-каталога и `warning` `appliance_catalog_dims` «уточните размеры встраивания по инструкции модели» (только если каталог реально использован). ПРОВЕРИТЬ МАСТЕРУ. (10, ревью этапа 1)
- **Проект строит, бриф проверяет:** шаблоны строят нишу по проекту (недостающее — каталог), бриф в шаблоны не входит. Проверка сравнивает требование (бриф, иначе каталог) с нишей, которую модуль строит той же функцией `parts.built_niche`. Не влезает — `error` `niche_too_small` с обеими цифрами. Для модулей без своей ниши (ПММ, мойка, варочная) строится пространство модуля: у ПММ ширина модуля и высота ряда плюс ножки, у остальных внутренняя ширина (`ящики.внутренняя_ширина`) и глубина корпуса. Ниша по брифу отличается от построенной в пенале или вытяжке — `warning` `niche_not_in_project` «перенесите размеры встраивания из брифа в проект». Позиция каталога не найдена и размеров встраивания нет — `warning` `appliance_no_data`. Брифа нет — `warning` `brief_missing`, ниши по каталогу, импорт не блокируется. ПРОВЕРИТЬ МАСТЕРУ. (10)
- **Приборы «в столешницу»** (варочная, мойка; список `техника_в_столешницу` в `construction.yaml`, МОК) лежат на столешнице: их ширина с внутренней шириной модуля не сравнивается, глубина сравнивается; разрешены в любом нижнем корпусном модуле без замечаний. ПРОВЕРИТЬ МАСТЕРУ. (10)
- **Состав техники:** приборы брифа и проекта одного вида сопоставляются сначала по модели, затем по порядку; несколько приборов вида без моделей — `warning` `appliance_pairing`. Под какие виды шаблон строит нишу, объявляет реестр (`Template.appliances`), позицию каталога отдаёт одна функция `parts.niche_item`. Встраиваемый прибор брифа (`built_in: true`) без пары в проекте — `error` `appliance_unbound`, если такой шаблон есть, иначе `warning` `appliance_no_template`. Прибор в ряду, который ему явно не подходит (вытяжка внизу, духовка вверху; `APPLIANCE_ROWS`), — `error` `appliance_wrong_module`; в подходящем ряду, но в модуле без ниши под него (духовка в `base_door`) — `warning` `appliance_no_niche`. Прибор проекта без пары в брифе — `warning` `appliance_not_in_brief`. Вытяжка — объект `appliances.hood` (виды `built_in`, `telescopic`). Виды `техника_в_столешницу` сверяются при загрузке с `APPLIANCE_KINDS`; тест проверяет, что перечень схемы брифа входит в константу. ПРОВЕРИТЬ МАСТЕРУ. (10)
- **Нечитаемые размеры техники в проекте** при непостроенном модуле — `error` `appliance_size`; если `module_build` уже назвал тот же сбой, не дублируются. (10)
- **Скрипт проверки брифа грузится как модуль** по пути от пакета (`skills/kitchen-brief/scripts/check_brief.py`) и остаётся только на стандартной библиотеке. (04)

## Проверки проекта

- **Модуль `kitchen.checks`, находка `Finding`** (код, `error`/`warning`, субъект, русское сообщение, значение, предел). Сбой расчёта шаблона одного модуля — находка `module_build`, а не обрыв: остальные проверки идут дальше. Импорт отклоняет проект с `error` и пишет `warning` в журнал. `api.check_project(path)` — те же находки без БД. (10)
- **Сумма ряда:** ширины модулей ряда + смещение углового модуля соседней стены (нижнее — ключ мастерской, верхнее — глубина верхних плюс толщина фасада углового, `parts.upper_corner_offset`, тикет 50) + ширины пеналов, записанных в других рядах той же стены (и тогда, когда в ряду есть свой пенал); допуск — `допуск_стены`. Расхождение в любую сторону — `error`, с обеими цифрами и разницей. Ряд без модулей и стена без рядов проверяются так же, если ряд записан. ПРОВЕРИТЬ МАСТЕРУ. (10)
- **Внутренняя глубина ящика — глубина корпуса модуля** (задняя стенка накладная, фасад снаружи). Нужная глубина — одно правило (`parts.drawer_depth_shortfall`): дно ящика по формуле мастерской плюс толщина задней стенки ящика (490 + 16 = 506 мм), но не меньше `длина_направляющей` (500 мм). Её зовут проверки шаблонов с ящиками (`Template.drawers`) и `drawer_parts`; ошибка — `drawer_depth` с цифрами; при ней расчёт модуля не запускается. ПРОВЕРИТЬ МАСТЕРУ: нужна ли глубина с задней стенкой или хватает направляющей. (10, 34)
- **Рабочее поле листа:** лист минус `обрезка_по_периметру` с двух сторон (2800×2070 → 2780×2050). Запрет поворота — по текстуре материала (`текстура` в `materials.yaml`), для всех деталей из него; длина текстурной детали — вдоль направления «вдоль N». Проверяются все детали листовых материалов (в том числе ХДФ и заглушки); фасады МДФ и столешница не проверяются. Одна функция для проверок и раскроя — `checks.part_fit_findings`. Непонятная запись текстуры — ошибка мастерской. (10, 12)
- **«Без задней стенки»:** `warning` для модуля с боковинами без задней стенки (мойка и `without_back`); модуль без корпуса (ПММ) не в счёт. (10)
- **`part_too_small`** (тикет 45): деталь, у которой длина или ширина меньше `мин_размер_детали` (толщина не проверяется; фасады — тоже детали), — `error`, субъект — метка модуля, текст «Н1-полка 540×1 мм: меньше 30 мм — проверьте размеры модуля», по находке на деталь. Проверка идёт в `parts.build_module` до присадки (`PartTooSmallError`): иначе у узкого модуля находкой стало бы «отверстие выходит за деталь», а не причина. Поэтому `kitchen parts` и `cut` на таком модуле тоже падают, а не считают невозможную деталь. Отклонение от тикета: `base_door` шириной 35 даёт именно `part_too_small` (раньше проверка присадки заслоняла её). (45)
- **Решение мастера 2026-11-15 об остановке на `part_too_small`:** так и надо. Мастер не задаёт детали: он пишет высоту и глубину модуля, ширина — стандартная, иногда подгоняется под длину стены; размеры полок и прочих деталей считает программа. Модуль, дающий деталь меньше минимума, — опечатка в размере модуля (35 вместо 350), а не проект, по которому что-то считают. Программа должна снимать с мастера расчёты; текст находки в терминах модуля, а не детали, — отложенная находка (`deferred.md`, тикет 45). (45)
- **Решение мастера 2026-11-15 о заказе, у которого ошибки появились после правки мастерской:** сейчас без предупреждения — так нормально. Бэклог: версии мастерской (заказ хранит версию данных мастерской, по которой посчитан, и правка файлов мастерской не меняет молча уже посчитанные заказы). (45)
- **Нормализация меток** (`checks._label_key`): NFKC (полноширинные цифры и буквы), удаление невидимых символов (категория Cf: U+200B, U+FEFF, мягкий перенос), пробелы по краям, регистр, латинские двойники кириллицы — теперь и «Y»/«У». Повтор после нормализации — `duplicate_label`. (45)
- **Повтор меток → `OrderError`** — одна функция `api._require_unique_labels`, её зовут `_build_parts` и `_build_cut`. (45)
- **`row_layouts` не возвращает последний вариант.** Отступы пеналов, не сошедшиеся за отведённое число проходов, — `OrderError` «Раскладка рядов стены не сходится». Сам алгоритм изменён: отступ пенала записывается сразу, как ряд его посчитал (раньше два пенала в разных рядах на одном месте менялись местами на каждом проходе и «сходились» только за счёт последнего варианта). Суммы рядов и длины не изменились (все тесты прежние). (45)
- **`kitchen check <заказ>|--project <файл>`** (тикет 36): находки без расчёта выводов, журнал и `status.md` не пишет. Коды выхода только у `check`: 0 — ошибок нет, 1 — есть `error` или файл — JSON, но проект отклонён схемой/`order` (его надо править; решение координатора), 2 — команда не выполнилась (нет заказа или проекта, битый JSON, мастерская не загрузилась). В тексте ошибки идут раньше предупреждений; в `--json` порядок тот же, что у `parts` (`findings` как есть). Предупреждение о брифе новее — поле `brief_note` в `CheckResult` (строка из `_order_project`, как у `parts`). `api.check_project` и `api.check_order` строят результат одной функцией и берут проект тем же `_project_file`/`_order_project`, что `parts`; импорт зовёт те же `parse_project` и `run_checks`. Разбор файла (не объект, `order`, схема без поля `version`) — одна функция `api.parse_project_file`, её зовут импорт и `check`/`parts`; `source.version` файла — только целое ≥ 1. (36)

## `kitchen parts` и общие позиции

- **`kitchen parts <заказ>`** берёт текущую версию проекта из БД, проверки идут с последним брифом заказа (`source.brief_id`), у версии записанный бриф — `source.version_brief_id`; бриф новее — предупреждение с советом переимпортировать. `--project` — файл без БД; бриф берётся из заказа, если он есть, иначе `brief_missing`; версия-источник — хеш файла и `version` из файла. Заказ и `--project` вместе или ни одного — ошибка. (11)
- **Находки с `error` `parts` не прерывают** и не меняют код выхода: команда — просмотр; импорт такой проект отклоняет. Сбой расчёта шаблона обрывает команду с сообщением. Строка «Проверки: N ошибок, M предупреждений» идёт сразу после строки источника. (11)
- **Общие позиции — `kitchen.common`, ключи `общие_позиции` (МОК).** Результат — список `common` в `PartsResult`, в `hardware` не входит. ПРОВЕРИТЬ МАСТЕРУ. (11)
- **Цоколь:** фронт всех модулей нижних рядов и пенала (из любого ряда, в том числе когда в нижнем ряду свой пенал; место пенала — по его отступу от начала стены в своём ряду) и ПММ без глухой части угловых модулей + `запас_на_стыки` 5%, штуками по 4 м вверх до целой. У Петрова 2800 + 1200 − 600 = 3400 мм → 1 штука. Пустое место в сумму ряда входит, в цоколь, шину и LED — нет; в столешницу — только с `under_countertop` (оно же не входит в цоколь). Хвост основания («без пустых мест 600 мм») есть только при пустых местах; у столешницы в хвосте только места без `under_countertop`. Пенал на стене без нижнего ряда входит в цоколь (`common._entries`). ПРОВЕРИТЬ МАСТЕРУ. (11, ревью этапа 1, 32)
- **Шина и LED:** длина верхних рядов по модулям своего ряда без пенала (3400 мм у Петрова) + тот же запас; шина штуками по 2 м, LED вверх до кратного `led.округление_метров` (1 м), блок питания по `метров_на_блок: 5`. LED только при `led: true`. ПРОВЕРИТЬ МАСТЕРУ. (11)
- **Навесы** считают шаблоны верхних модулей; строка `hangers` в общих позициях справочная (`in_hardware: true`). (11)
- **Столешница — решение мастера (MVP, тикет 35): общая длина без нарезки на куски.** Длина — сумма ширин нижних модулей всех стен; пенал из любого ряда не входит, угловой модуль на своей стене берётся целиком, без смещения (угол «встык»). Листов = длина / длина листа столешницы вверх до целого, цена — за лист; пропил не учитывается. Одна функция `common.size_countertop` (`CountertopSize`) отвечает общим позициям, раскрою (`CutResult.countertop`), закупке и смете. У Петрова 3400 мм → 1 лист 4100×600. Только при `materials.countertop`; неизвестный id — ошибка. Глубину столешницы с шириной листа не сверяем. ПРОВЕРИТЬ МАСТЕРУ. (11, ревью этапа 1, 35)
- **Столешница только для всего проекта (тикет 18, второе ревью).** Переопределение `countertop` в `materials` ряда или модуля — `error` `countertop_override` проверки проекта (импорт отклоняется): «столешница задаётся только для всего проекта (materials.countertop)». Цену, раскрой и закупку всегда считал `common.size_countertop` по `materials.countertop` проекта, переопределения они не видели, и КП с ними расходилось бы с ценой. Неизвестный id столешницы проекта — ошибка `size_countertop`, как и раньше. Петров переопределений столешницы не имеет. (18)
- **Фасады по цветам:** нижний ряд и пенал красят нижние фасады, верхний ряд — верхние; без цвета — группа «без цвета». Цвет — свойство модуля: `parts.resolve_materials` и `parts.facade_color` — единственное место, откуда его берут площадь по цветам и закупка. (11, ревью этапа 1)

## Раскрой

- **Модуль `kitchen.cutting`, `api.cut_from_order` / `cut_from_project`, CLI `kitchen cut <заказ>|--project`.** Результат хранит версию-источник, пометку мока, пропил, обрезку, макс. рез. (12)
- **Пропил — решение мастера: дробный округляется вверх до целого мм** (`Saw.kerf_mm`), и раскрой считает с ним везде (зазор между деталями, ширина линии реза в PDF; столешницу пропил не затрагивает). Пропил 3.2 учитывается как 4, 4.5 — как 5; результат раскроя несёт предупреждение «пропил 3.2 мм учтён как 4 мм» (текст, JSON; в карте раскроя указан пропил из `equipment.yaml`). Целый пропил (в том числе `4.0`) — без предупреждения; записанное значение показывается без потери цифр (`4.0000001`). То же предупреждение (одна функция `cutting.kerf_warnings`) стоит в `warnings` закупки, сметы и production: число листов в них посчитано с учтённым пропилом. `обрезка_по_периметру`, `макс_длина_реза` и размеры листа — только целые. `CutResult.kerf` — учтённый, `kerf_declared` — записанный в мастерской. (33)
- **Пропил через увеличение:** к каждой детали и к рабочему полю прибавляется пропил; гильотинные алгоритмы `rectpack` (BSSF/BLSF/BAF × 6 правил разреза) с `merge=False`, 6 сортировок, 3 способа выбора листа: перебор 324 раскладок. (12)
- **Выбор раскладки:** меньше листов, затем больше площадь деталей на последнем листе, затем первый в порядке перебора; результат детерминирован. ПРОВЕРИТЬ МАСТЕРУ: нужен ли обратный критерий (максимально пустой последний лист). (12)
- **Оси листа:** `x` — вдоль текстуры, у нетекстурного — первая сторона листа. Поворот запрещён для материала с текстурой. (12)
- **Какие детали режутся:** только материалы из `листовые`. Фасады в раскрой не идут; столешница не режется: `CutResult.countertop` — общая длина и число листов из `common.size_countertop`. Деталь неизвестного материала — ошибка; деталь больше рабочего поля — `OrderError` с маркировкой. (12)
- **Порядок резов:** у куска отрезается отход вокруг деталей, затем ищется сквозной рез (сначала вертикальный по наименьшему краю детали, иначе горизонтальный), левый/верхний кусок режется раньше. Раскладка без сквозного реза — `KitchenError`. Резы нумеруются с 1 на каждом листе; пропил занимает `position … position + пропил`. ПРОВЕРИТЬ МАСТЕРУ: подходит ли порядок «сначала вертикальные». (12)
- **Торцовка у края нужна всегда**, когда деталь не у края куска (`minx > x0`, `miny > y0`), даже при зазоре тоньше пропила: иначе деталь выйдет больше номинала. Порога «минимальная полоса отхода» нет. Проигрыватель резов в тестах строгий (деталь ровно своего размера) и гоняется по всем раскладкам всех эвристик. ПРОВЕРИТЬ МАСТЕРУ: возможно, удобнее, чтобы такой рез заменял обрезку периметра с этой стороны (на листе 1 у Петрова рез по x=2778 снимает 2 мм у края поля). (12, 13)
- **Обрезка по периметру (10 мм)** не нумеруется: мастер сначала подрезает лист. Длина реза проверяется для всех пронумерованных резов и для подрезки целого листа (длиннее `макс_длина_реза` — ошибка). (12)
- **Использование листа** = площадь деталей / полная площадь листа; отход = площадь листов − площадь деталей. (12)
- **Эталон Петрова (мок):** ЛДСП белый — 4 листа (71 деталь, 18.111 м², 78.1%), ХДФ — 2 листа (11 деталей, 5.2302 м², 45.1%), столешница 1 лист (общая длина 3400 мм). ПРОВЕРИТЬ МАСТЕРУ. (12)

## PDF

- **Шрифт — DejaVu Sans и Bold** в `engine/kitchen/fonts/` с лицензией; системные шрифты не нужны. Вызывающий ставит `FONT` перед текстом. (грилинг, 13)
- **Общий слой `kitchen.pdf.PdfDocument`:** A4 книжный; водяной знак поверх содержимого полупрозрачным (alpha 0.2), колонтитул «Заказ · версия проекта N · дата · стр. i из N», при моке — красная строка «МОК-ДАННЫЕ — НЕ ДЛЯ КЛИЕНТА». Без мока — ни знака, ни строки. PDF детерминирован. Зависимости: `reportlab`, `pypdf` (только dev). (13)
- **Карта раскроя — `kitchen.cutting_pdf`:** страница на лист (плюс продолжения), столешница не входит; заказ без листовых деталей — одна пустая страница. Схема в масштабе, обрезка пунктиром, резы красным, ширина линии реза — пропил. Под схемой списки деталей и резов: ширина колонки по самой длинной строке, кегль 6.5 → 6 → 5.5 пт (`MIN_FONT`), не поместилось — страница-продолжение «лист N, продолжение». ПРОВЕРИТЬ МАСТЕРУ: читаемость и порядок на печати. (13)
- **Подписи схемы без наложений:** `scheme_labels` считает подписи деталей и рамки номеров резов вместе в масштабе страницы (`scheme_scale`, одна функция для рисования и тестов). Номер реза не закрывает подписей; нет места — подпись детали укорачивается («маркировка размеры» → «маркировка» → номер), частично закрытых подписей не бывает. Отодвинутый номер связан с резом пунктирной выноской в обход подписей и рамок (выноски могут пересекаться между собой и с другими резами); не удалось разместить — карта не пишется, ошибка. ПРОВЕРИТЬ МАСТЕРУ: читаемость выносок. (13)
- **Карта присадки — `kitchen.drilling_pdf`:** `kitchen drilling <заказ>` → `orders/<заказ>/out/drilling-map.pdf`. Сетка 2×2: на странице 2–4 схемы (`page_sizes`: не больше четырёх, при двух и более деталях не меньше двух — 5 → 3 + 2), каждая деталь своей схемой, зеркальные не объединяются, детали без отверстий страниц не занимают, заказ без отверстий — одна страница «Деталей с отверстиями нет». Раскладка страниц (`drilling_pdf.map_layout`, публично — `api.drilling_map_layout`) считается отдельно от рисования, её же проверяют тесты: строки с кеглем и шириной, контур, базовые линии, цепочки с рамками подписей. На схеме: контур в масштабе в осях модуля (вправо +x, если x в плоскости детали, иначе +y — перед справа; вверх +z, иначе −y — лежачая деталь видна сверху, перед внизу); под заголовком — с какой стороны смотрим и с какой грани сверлить (из `from_face` отверстий: «вид с лица (+y)», «сверлить: с тыльной стороны (-y, обратная) — чашка петли»; боковина видна слева, -x), базовые кромки — толстой оранжевой линией, отверстия в пласть — кружки (сквозные залиты; конфирмат синий, чашка красная, планка зелёная, полкодержатель фиолетовый, направляющая бирюзовая — тикет 20), в торец — отрезок вглубь от кромки; под схемой и слева — цепочки размеров от базовых кромок (подписи — расстояние от базы, близкие уходят на следующую строку), под ними таблица отверстий: назначение, пласть или торец с гранью, Ø×глубина, расстояния от двух базовых кромок. В шапке — строка сверки с фурнитурой. Строки подгоняются: сначала кегль до минимума (заголовок 7.5 → 5.5 пт, текст 6 → 5 пт), затем короткий вариант (заголовок без имени детали, подзаголовок без материала, сторона сверления гранями, сверка короткими именами); не помещается и так — ошибка, как и схема или таблица, которой не хватает ячейки; обрезанных строк нет. Подписи цепочек не налезают друг на друга и на текст: масштаб уменьшается, пока строк подписей хватает, поля у контура — под половину самой широкой подписи. ПРОВЕРИТЬ МАСТЕРУ: читаемость на печати и обозначения граней (`-x`, `+y`). (19)
- **Карта кромления:** `kitchen edges <заказ>` → `orders/<заказ>/out/edging-map.pdf`. По строке на деталь с кромкой, колонки L1/L2/W1/W2 с id кромки, пустые — тире; итог по типам; строки переносятся целиком с повтором заголовка. Метраж — из `parts`, отдельной формулы нет. ПРОВЕРИТЬ МАСТЕРУ: читаемость таблицы. (14)

- **Виды кухни в PDF** (решение мастера 2026-11-15): вид на каждую стену спереди и план сверху рисует общий PDF-слой из расстановки тикета 23, без three.js и новых зависимостей; аксонометрии нет. PDF открывается в любом мессенджере, когда HTML не открылся. Тикет 41.
- **three.js встроен в HTML** (решение мастера 2026-11-15): одним обычным скриптом, без сети и подгрузки модулей. HTML скачивают и открывают в браузере на iPhone и Android. Тикет 42.

## Выводы и закупка

- **`kitchen production` выпускает все документы цеха** (решение мастера 2026-11-15): раскрой, кромку, закупку, сборочный лист и чек-лист выезда; отдельные команды остаются. Карта присадки в `production` не входит — только своей командой `kitchen drilling` (уточнение мастера 2026-11-15, тикет 22). Тикеты 22 и 40.

- **Учёт выводов:** таблица `outputs`; путь относительно `KITCHEN_HOME`, версия-источник; вид — `store.OutputKind` (`cutting`, `edging`, `purchase_md`, `purchase_json`, `estimate_md`, `estimate_json`, `quote_pdf`, `quote_json`, `drilling`, `assembly`). Повторный вывод заменяет файл и запись. `--project` файлов не пишет. `cut_from_order` ничего не пишет, PDF и запись делает `cut_and_save`. (13, 14, 15)
- **Устаревшие выводы (тикет 24):** вывод устарел, если `source_version` меньше текущей версии проекта; смена данных мастерской вывод не помечает (вопрос М21 отложен). ПРОВЕРИТЬ МАСТЕРУ. Команда пересчёта каждого вида — в одном реестре `store.OUTPUT_RECOMPUTE` (`api.OUTPUT_RECOMPUTE`): вид → название и команда CLI; `cutting` → `cut`, `edging` → `edges`, `purchase_*` → `purchase`, `estimate_*` → `estimate`, `quote_*` → `quote` с подсказкой `--days <рабочих дней>` (`Recompute.args`: срок вписывает мастер, команда без него не запустится), `drilling` → `drilling`. Тест-ограждение требует запись для каждого `OutputKind` и существующую команду в CLI. `status.md` получает раздел «Устарело» после «Версии проекта»: по строке на вывод (в порядке записи в БД) с названием, файлом, версией и командой; пусто — «Пока ничего.». Устаревшая запись неизвестного вида (БД от более нового движка) — русская `OrderError` «обновите kitchen», а не голый `KeyError`; `status` в этом случае не пишется. Тот же список — поле `stale` в JSON. Строка — на каждую запись таблицы, поэтому `purchase_md` и `purchase_json` показываются двумя строками с одной командой. (24)
- **Сохранение:** PDF пишется во временный файл и переименовывается после успешной отрисовки. Готовый файл устанавливается под блокировкой записи SQLite; при ошибке регистрации прежний файл восстанавливается. Проект изменился во время расчёта — команда просит повторить. Раскрой, кромление, закупка и присадка используют один механизм; `kitchen production` (без присадки) готовит все выводы из одного снимка и откатывает каждый файл при ошибке, резервные копии при неудаче восстановления сохраняются. Атомарность двух хранилищ при аварийном завершении не гарантируется. (13, 14, 15)
- **Закупка:** листы — из раскроя, столешница — из `common.size_countertop`, кромка — из `parts`. Минимум продажи — условие «метраж от N м» в `materials.yaml` (неизвестное — ошибка); после минимума — вверх на шаг мастерской. (15)
- **Фурнитура в закупке:** позиции модулей и общие одного id суммируются до расчёта упаковок, `in_hardware` второй раз не учитывается; LED — метрами. Цена в `hardware.yaml` — цена упаковки, `упаковка` — изделий (или метров) в ней. ПРОВЕРИТЬ МАСТЕРУ: цены за упаковку или за штуку. (15)
- **Фасады в закупке:** площадь по паре материал и цвет, по нижнему или верхнему ряду (пенал — нижний), с учётом переопределений; округление до 0.0001 м². Сумма позиции — до копеек, суммы магазинов и итог — из них. `purchase.md` и `purchase.json` — из одной модели, с версией, суммами, пометкой мока и предупреждениями. (15)

## Смета

## Экономия

- **Решения мастера (тикет 17).** Замены в `economy.yaml`, каждая применяется ко всем подходящим модулям: карусель → полка (угловой нижний без карусели, одна полка с полкодержателями); Tandembox → двери с полкой (`base_drawers` → `base_door`, двери по правилу ширины, 1 полка; ящик в пенале не трогается); подъёмник → распашная дверь (`wall_lift` → `wall_door`; у вытяжки и сушки `contents.lift` убирается, двери на петлях); без ведра (из мойки убирается вставка-ведро); без сушки (`wall_dryer` → `wall_door` с полкой). Разница — на правило: одна строка на замену со списком модулей, разница = цена «как в проекте» − цена с одной этой заменой; итог — цена со всеми предложенными заменами сразу и разница с ценой «как в проекте». Сумма разниц может не совпасть с итогом (целые листы, округление): это показывается в смете. Замена с разницей ≤ 0 не предлагается (ни в списке, ни в итоге), во внутренней смете остаётся строка «не удешевляет, не предложена» с разницей. Правило, подходящее нескольким модулям и не строящееся на одном, применяется к остальным, про этот модуль — сообщение с меткой и причиной. (17)
- **Решение мастера: «подъёмник → распашная» — двери по правилу ширины.** У модуля 600 мм две двери, поэтому петель и ответных планок больше, чем с подъёмником (у Петрова 28 петель вместо 20). Подъёмник одним цельным фасадом заменяется дверями на петлях, а не одной дверью. (17)
- **Как считается.** `kitchen.economy.apply_rule` заменяет модули в глубокой копии проекта и проверяет каждый заменённый модуль `parts.build_module`; цену копии считает тот же путь, что смету (`api._priced`: детали → раскрой → закупка → смета; бриф не нужен). Копия нигде не сохраняется: версия проекта и `project_versions` не меняются, в БД пишется только вывод сметы. Заменить нечего (модуль не меняется) — модуль не в списке. Предложенные замены в итоге применяются по очереди в порядке файла к одной копии; сообщение «не строится» из итога добавляется, если его ещё не было. Детали копии со всеми предложенными заменами — `api.economy_parts_from_project` (для проверок и КП тикета 18). (17)
- **Формат правила в `economy.yaml` (решение исполнителя).** `замены:` — список правил: `id`, `название`, `текст_клиенту`, `случаи`. Случай — `где` (`шаблон`; по желанию `подъёмник: true` — у модуля есть `contents.lift`, `вставка: id` — вставка есть в `contents.inserts`) и `на` (`шаблон` — новый шаблон, `полок`, `убрать_подъёмник`, `убрать_вставку`). Первый подошедший случай правила применяется к модулю. Новый шаблон собирает наполнение заново: остаётся только указанное в `на` (у `wall_lift` → `wall_door` полок не указано: `wall_door` строит полку по умолчанию, одну). Карусель в явной форме `contents.inserts: [corner_carousel]` правило «карусель → полка» убирает (`убрать_вставку`). Неизвестный ключ, шаблон или id вставки, шаблон замены в другом ряду, чем исходный, повторный id правила и пустое `на` — ошибка загрузки (`check-workshop`) с файлом и ключом. Метка модуля, его размеры, материалы и техника проекта при замене сохраняются. Файл — восьмой в мастерской: `mock_files`, плашка и `check-workshop` его учитывают. (17)
- **Вывод.** `estimate --economy` пишет вариант в те же `estimate.md` (раздел «Экономия») и `estimate.json` (ключ `economy`); без `--economy` раздела и ключа нет, повторный `estimate` без флага заменяет файлы. `--economy` работает и с `--project` (файлов не пишет). Модель — `EconomyVariant`: `price_as_is`, `price`, `saving`, `replacements` (id, название, текст клиенту, модули, цена с одной заменой, разница), `not_offered`, `problems`. ПРОВЕРИТЬ МАСТЕРУ: цена с одной заменой показана в строке рядом с разницей. (17)
- **Полка в `base_corner` (первый срез).** `contents.shelves: 1` у нижнего углового даёт одну полку (по правилам `base_door`: 1016×540 у 1050 мм) и 4 полкодержателя вместо карусели; `0` или без наполнения — карусель, как раньше; полка вместе со вставкой карусели — ошибка «неподдерживаемое наполнение». Ручной эталон — `tests/golden/base_corner_1050_shelf.json` (ПРОВЕРИТЬ МАСТЕРУ: полка 1016 мм в модуле 1050 мм при глухой части угла; нужны ли опора или вторая полка). Эталон без замены `base_corner_1050` не менялся. (17)

- **Решения мастера (тикет 18, 2026-11-15).** Срок изготовления и монтажа для клиента вписывает мастер: `kitchen quote <заказ> --days N` (рабочих дней, целое больше нуля, обязательно), движок срок не считает; в КП — «Срок изготовления и монтажа: N рабочих дней». Состав кухни — строка на модуль словами в порядке стен и рядов, ниже корпус, цвета фасадов (нижние и верхние), столешница; без марок фурнитуры. С `--economy` — две цены («как в проекте» и «экономия»), одна общая разница и список замен текстом для клиента (`текст_клиенту`) без сумм по строкам. Реквизиты из `master.yaml`: имя, телефон, город, статус, ИНН; «Предложение действует N дней» (мок 14). (18)
- **`master.yaml` — девятый файл мастерской** (`mock: true`, заглушки без реальных людей и организаций): `имя`, `телефон`, `город`, `статус` (`самозанятый` или `ИП`), `инн` (строка из 12 цифр в кавычках), `срок_действия_предложения_дней` (целое больше нуля). Загрузчик, `mock_files`, плашка и `check-workshop` его учитывают; замена — `MOCKS.md`. (18)
- **Цена и предоплата.** Итог КП — `price` сметы того же снимка версии, той же цепочкой (`api._estimate_run`: детали → раскрой → закупка → смета), которой считает `estimate`. Предоплата = итог × `предоплата` из `pricing.yaml`, до целого рубля (от половины вверх, `Decimal`); остаток = итог − предоплата, поэтому сумма точно равна итогу. Решение исполнителя: округление предоплаты до рубля (цена и так целая; копейки в КП не нужны). `предоплата` ограничена `0..1` в типе (`Pricing.prepayment`): доля больше единицы давала бы отрицательный остаток. (18)
- **Модель и вывод.** `quote.QuoteBody` — всё, что видит клиент; `api.QuoteResult` = `QuoteBody` + источник + `outputs` + пометка мока. В модели нет себестоимости, наценки, труда, расходников и сумм по строкам замен; `quote.json` — та же модель, что `--json`. `quote.pdf` и `quote.json` — виды `quote_pdf` и `quote_json`, сохраняются одним комплектом (`_save_outputs`), повтор заменяет файлы и записи; `--project` файлов не пишет; заказ и `--project` вместе — ошибка; `--days` проверяется до расчёта (`quote.check_days`, из командной строки — `quote.parse_days`: только целое десятичное, «2.5», «abc», «0», «-1» и отсутствие — одна русская ошибка). `--economy` с заказом пишет вариант в оба файла; в JSON ключа `economy` без флага нет. Колонтитул и водяной знак — общий PDF-слой (заказ, версия, дата, страница; плашка мока). (18)
- **Решения мастера после ревью (тикет 18, 2026-11-15).** (1) Наполнение называется словами без марок: подъёмный фасад — «с подъёмным фасадом», дверью не считается; вставки — «с поворотной каруселью», «с выдвижным ведром», «с сушкой для посуды»; бутылочница — по названию шаблона. (3) Техника — словами брифа: духовой шкаф, микроволновка, посудомойка, варочная панель, отдельностоящая плита, мойка и др.; вытяжка и «другая техника» в брифе слов не имеют. (18)

## Присадка

- **Наклейки не в MVP** (решение мастера 2026-11-15): мастер различает детали по проекту, распилу и кромлению. Тикет 21 — бэклог; `kitchen-production` наклеек не ведёт.

- **Решения мастера (тикет 19).** Сторона петель одной двери — необязательное поле наполнения модуля, по умолчанию слева; у угловых сторона следует из места в ряду; от стороны зависит, какую боковину сверлить под ответные планки. Три и больше петель: крайние чашки в 100 мм от торцов фасада, остальные делят промежуток поровну, округление до мм. Конфирмат — два отверстия: сквозное в пласти одной детали и в торце парной, оси совпадают; сверка: отверстий в пласть = в торец = конфирматов в фурнитуре. В присадку не входят подъёмник Aventos, навесы, ручки, опоры и стяжки; фасад подъёмника и фасад ПММ — без чашек. (19)
- **Одно правило подсчёта — модель соединений.** Шаблон называет соединения `geometry.Joint(plate, end)` (деталь `end` торцом на конфирматах к пласти `plate`: дно, крыша, царги, дно ниши и перегородки пенала, планка дна вытяжки — к обеим боковинам) и двери на петлях `geometry.HingedDoor(facade, side, side_part)` (маркировку боковины под планки называет шаблон через `parts.side_part_id`; присадка имён деталей не собирает). `kitchen.drilling.apply_drilling` (зовёт `parts.build_module` после шаблона; схема отверстия, соединения и двери — в `kitchen.geometry`, который не зависит ни от `parts`, ни от `drilling`, поэтому они не импортируют друг друга по кругу: `drilling` берёт `Part` только для типов) из них одним местом считает конфирматы и заглушки, петли, планки, саморезы на петли и ставит отверстия; шаблоны этих чисел больше не считают. Длина соединения — размер торца `end` по глубине модуля (по оси `y`), число конфирматов — по таблице `конфирматы_по_длине_соединения`; итог Петрова не изменился (102 конфирмата, 20 петель и планок, 330 саморезов). Позиции фурнитуры появляются, только если в модуле есть соединения или двери на петлях (у ПММ их нет, как раньше). (19)
- **Отверстие** — поле `holes` детали (`geometry.Hole`; грань `from_face` и сторона `edge_side` — перечни `Face` и `EdgeSide`): назначение (`confirmat`, `hinge_cup`, `hinge_plate`; с тикета 20 — `shelf_pin`, `runner`), пласть или торец (`surface`), грань сверления в осях модуля (`from_face`), у торца — сторона L1/L2/W1/W2 и положение по толщине, диаметр, глубина, сквозное ли, центр устья в координатах модуля (`geometry.Point`: целые мм, у полкодержателя — до десятых) и расстояния до двух базовых кромок (`from_base`, так же), у полкодержателя — `holds_shelf` (на нём лежит полка). У деталей без отверстий `holes` и `base_edges` пусты (`null`): эталоны `tests/golden/` сравниваются без этих полей (`tests/conftest.golden_dump`), детали и фурнитура в них не менялись. (19)
- **Базовые кромки — ключ `присадка.базовые_кромки` (МОК: нижняя, передняя, левая)**: три кромки, по одной на ось модуля, в порядке приоритета; деталь берёт первые две, чьи оси лежат в её плоскости (боковина — нижняя и передняя, дно и царги — передняя и левая, фасад — нижняя и левая). Иной список — ошибка загрузки. Левый и правый фасад поэтому отмеряются от левой кромки оба (у правого чашки в `ширина − 22`); боковины — от нижней и передней, зеркальны. ПРОВЕРИТЬ МАСТЕРУ: удобнее ли отмерять фасад от кромки петель. (19)
- **Конфирматы на соединении:** один — посередине соединения (планка дна вытяжки 40 мм — в 20 мм, царга 100 мм — в 50); два и больше — крайние в `отступ_от_лицевой_кромки` и `отступ_от_задней_кромки` (МОК 50 и 50), остальные поровну, округление до мм вверх от .5. Отступы больше длины соединения — ошибка модуля. По толщине — посередине торца (вверх от .5). Сквозное отверстие в пласти размечается с наружной грани детали (головка конфирмата и заглушка снаружи), глубина — толщина детали; в торце — `глубина_в_торец` (МОК 40), диаметры 7 и 5 (МОК). ПРОВЕРИТЬ МАСТЕРУ: место одного конфирмата и отступы. (19)
- **Петли:** чашка с тыльной грани фасада (`-y`), центр в `отступ_от_кромки_фасада` (22) от кромки со стороны петель, по высоте — по решению мастера; одна петля (если таблица её даст) — посередине фасада. Две двери — левая на петлях слева, правая справа. Ответные планки — на внутренней пласти боковины той же стороны, в `отступ_от_передней_кромки` (37) от передней кромки, `отверстий` (2) с шагом `шаг` (32) симметрично относительно высоты чашки. Больше одной планки на петлю («по 2 на петлю») присадка не размечает: отверстий планок нет, в `parts` одно предупреждение на расчёт (`drilling.plate_warnings`), карта присадки отказывает сверкой и называет причину. Фасад ниже двух отступов от торцов — ошибка модуля. ПРОВЕРИТЬ МАСТЕРУ: отступы и шаг планки по каталогу. (19)
- **Сторона петель — `contents.hinge_side`: `left` или `right`** (значения английские, как `kind` ряда; ПРОВЕРИТЬ МАСТЕРУ). Задаётся только у модуля с одной дверью на петлях (`base_door`, `wall_door`, мойка и пенал с одной дверью); у двух дверей, подъёмника, ящиков, бутылочницы — ошибка модуля; у углового — ошибка «сторона следует из места в ряду». (19)
- **Отверстие внутри детали:** устье на своей грани, окружность в пределах детали, глубина не больше размера по оси сверления; отверстия в пласти одной детали не пересекаются (глухие с противоположных пластей — только если их глубины вместе больше толщины; сквозное пересекается с любым), встречные отверстия в торцах не сходятся. Иначе — ошибка модуля (`OrderError`, в проверках — находка `module_build`). Отсюда новое поведение: на крошечных модулях (ширина или глубина около 100 мм и меньше) встречные отверстия конфирматов 40 + 40 мм в торцах дна или царги сходятся, и модуль, который раньше строился, теперь — ошибка модуля; физически так и есть. Другие ошибки модуля из присадки: фасад ниже двух отступов чашек от торцов, отступы конфирматов больше длины соединения. (19)
- **Сверка присадки — `drilling.reconcile`:** отверстий в пласть и в торец = `confirmat_7x50`, чашек = `hinge_71B3550`, отверстий планок = планок × `отверстий`, отверстий полкодержателей = `shelf_pin_5` × `отверстий_в_ряду` (ряд на полкодержатель; присадка ставит 4 ряда на полку, поэтому при `полка.полкодержателей` ≠ 4 карта отказывает и называет причину), отверстий направляющих = `tandembox_M_500` × 2 направляющие × число расстояний `отверстия_от_передней_кромки` (тикет 20); расхождение — `OrderError` с цифрами. Петров: 102, 102, 20, 40, 120 = 24 × 5, 24 = 4 × 6. Короткое имя для строки сверки — поле `short` самой сверки (`DrillingCheck`), а не отдельный список по позициям: новая сверка не может пропасть из короткой строки (20). Результат — `api.drilling_from_order` / `drilling_from_project` (`DrillingResult`: детали с отверстиями по модулям, строки сверки, версия-источник). (19)
- **Команда `kitchen drilling <заказ>|--project`, `--json`:** для заказа — PDF и вывод вида `drilling` (`api.drilling_and_save`, тот же `_save_output`, что у раскроя; запись в `OUTPUT_RECOMPUTE` — «карта присадки»); `drilling_from_order` и `--project` файлов не пишут; заказ и `--project` вместе или ни одного — ошибка. В `kitchen production` присадка не входит (решение мастера 2026-11-15, тикет 22). (19)
- **Решения мастера (тикет 20, 2026-11-15).** Полкодержатели: на каждой боковине спереди и сзади ряд из `отверстий_в_ряду` (5) с шагом `шаг` (32); высота полки (`полка.высота`, `полка.шаг`) не меняется; диаметр 5. Центр отверстия под полку — на радиус штыря ниже нижней пласти полки (верх штыря = низ полки, полка в цехе на высоте модели): ключ `центр_ниже_полки` (МОК 2.5 = радиус Ø5). В ряду по два шага выше и ниже отверстия под полку; ряд у дна или крыши сдвигается целиком на целые шаги, отверстие под полку остаётся в ряду (см. ниже). Направляющие Tandembox — по каталогу Blum, значения МОК. (20)
- **Полка и ящик в модели присадки.** Шаблон называет полку на полкодержателях `geometry.PinnedShelf(shelf, sides)` (`parts.pinned`: `base_door` и всё, что строится через него, и верхняя полка пенала) и ящик на направляющих `geometry.DrawerRunners(bottom_z, sides)` — его добавляет `parts.drawer_parts`, одна функция для `base_drawers` и пенала: она теперь кладёт детали ящика и направляющие прямо в результат шаблона. Число полкодержателей и комплектов Tandembox по-прежнему считает шаблон (как до тикета), присадка только ставит отверстия, а сверка сравнивает их с закупкой. Петров: детали и фурнитура не изменились (24 полкодержателя, 4 комплекта). (20)
- **Ряд полкодержателей.** Отверстия — с внутренней пласти боковины (у левой `+x`, у правой `-x`), глубина `глубина` (МОК 10). Отступы рядов — от кромок полки: передний в `отступ_от_передней_кромки_полки` (МОК 37) от её передней кромки, задний в `отступ_от_задней_кромки_полки` (МОК 37) от задней; так ряд идёт за полкой при любом `полка.отступ_спереди` (при 20 передний ряд — в 57 от кромки боковины, мимо линии ответных планок 37). Ряд вне глубины полки — ошибка модуля с названием обоих ключей. Центр отверстия под полку — `центр_ниже_полки` ниже её нижней пласти: координаты таких отверстий — до десятых мм (полка на 300 — 233.5…361.5), ключ задаётся в мм до десятых, не меньше 0, иначе ошибка загрузки. На одной линии с ответными планками ряд второй полки (597.5, 629.5) сходится с планками верхней петли (602, 634) — ошибка модуля «пересекается», как у любых пересекающихся отверстий (тикет 19), а не молча пропущенное отверстие. ПРОВЕРИТЬ МАСТЕРУ: отступы рядов по вашему кондуктору. Число отверстий в ряду — нечётное (иначе среднего нет), ошибка загрузки. (20)
- **Ряд у дна или крыши сдвигается целиком на целые шаги (решение мастера).** Если отверстие ряда выходит за боковину или заходит под торец детали, прикреплённой к ней конфирматами (дно, крыша, царга, дно ниши, перегородка; касание допустимо), весь ряд сдвигается на шаг, затем на два, пока не встанет целиком; отверстие под полку остаётся в ряду, отверстий по-прежнему 5, сверка «отверстий = полкодержателей × 5» точна. Пример: `wall_door` 960 с полками 300, 600, 900 — ряд верхней полки 833.5…961.5 сдвигается вниз, 801.5…929.5. Не встаёт ни при каком сдвиге (отверстие под полку само под дном) — ошибка модуля. Окружность внутри грани — одна проверка `drilling._fits` и для отверстия «внутри детали», и для сдвига ряда; «под торцом прикреплённой детали» — `drilling._under`, ею же после расстановки проверяются все полкодержатели и направляющие: направляющая под дном корпуса (`над_дном_ящика: 0`) — ошибка модуля. (20)
- **Направляющая Tandembox:** на внутренней пласти каждой боковины отверстия в `отверстия_от_передней_кромки` (МОК 37, 261, 453) от передней кромки боковины, на высоте дна ящика (`ящики.высота_дна`, то есть та же высота, что у детали «дно ящика») плюс `над_дном_ящика` (МОК 6), Ø5×13. Список — непустой и по возрастанию, иначе ошибка загрузки. ПРОВЕРИТЬ МАСТЕРУ: схема крепления по каталогу Blum для вашей направляющей. (20)
- **Таблица отверстий карты:** три и больше одинаковых отверстий подряд на одной линии (то же назначение, место, Ø×глубина; одно расстояние общее, другое растёт) — одна строка с номерами «15–19» и расстояниями «1633.5…1761.5 шаг 32» (шаг ровный) или списком «37, 261, 453»; так сгруппировались и отверстия планок одной боковины. У сдвинутого ряда полкодержателей (отверстие под полку не посередине) строка кончается «под полку 897.5». Отметки на схеме — по одной на отверстие. Иначе боковина пенала (27 отверстий) не помещалась в ячейку. Строка сверления, если не помещается и короткая, печатается без назначений («сверлить: -x видимая, насквозь; +x обратная»): назначения есть в таблице. Петров: карта — те же 65 деталей на 17 страницах. Перемычка 0 мм между глухими отверстиями с противоположных пластей (8 + 8 на 16) по-прежнему не пересечение — вопрос мастеру остаётся. (20)

## Сборочный лист

- **Решения мастера (тикет 22, 2026-11-15).** Порядок этапов — ключ `construction.yaml` `сборка`; числа в строках шагов движок берёт из модели соединений и фурнитуры модуля. Где ставится позиция — `hardware.yaml` `ставится: цех | объект` (нет ключа — «цех»; МОК: опоры, ручки, навесы — «объект»): сборочный лист — «цех», чек-лист выезда (40) — «объект». `kitchen production` выпускает раскрой, кромку, закупку, сборочный лист (и чек-лист выезда); карта присадки — только своей командой. Модуль без корпуса (фасад ПММ) — одна строка «корпуса нет»; пустой проект — страница «Модулей нет».
- **Ключ `сборка` — список из фиксированного набора этапов** (`models.ASSEMBLY_STAGES`: `корпус`, `задняя_стенка`, `полки`, `ящики`, `фасады`, `ручки`, `опоры`): неизвестный этап, повтор или пропуск — ошибка загрузки с именем этапа; ключ обязателен. Этап без строк у модуля пропускается. `ставится` не из двух значений — ошибка загрузки. (22)
- **Модель сборки модуля — `parts.AssemblyPlan`** в `ModuleParts.plan` (соединения, двери на петлях, полки, ящики, саморезы задней стенки; в JSON не выводится) и `ModuleParts.hardware` (вся фурнитура модуля, «цех» и «объект»; сумма по модулям равна `PartsResult.hardware`). `golden_dump` поле `hardware` модуля исключает: эталоны знают только итог проекта. Саморезы задней стенки считает `build_base_door` (`TemplateOut.back_screws`), без саморезов петель, ящиков и заглушки угла. (22)
- **Строки шагов:** `корпус` — по детали `end`: «Н1-дно к Н1-бок-Л, Н1-бок-П — 4 конфирмата» (число — отверстия в торец этой детали, сумма по модулю равна конфирматам модуля); `задняя_стенка` — «Задняя стенка Н1-зад — 18 саморезов»; `полки` — «Полкодержатели — 4 шт, полки: Н1-полка»; `ящики` — «Направляющие <название> — N компл., ящики: <дно ящика каждого>»; `фасады` — «Петли <название из hardware.yaml> — N шт, фасады: …» (слово «Петли» перед названием дословно по тикету) и «<название подъёмника> — N шт, фасады: …». (22)
- **Ручки и опоры в шагах — только если мастер отметил позицию «цех»:** «Ручки <название> — N шт, фасады: …», «Опоры <название> — N шт»; при «объект» этап пропускается. Решение агента, тикет это не называет. ПРОВЕРИТЬ МАСТЕРУ. (22)
- **JSON `kitchen assembly --json`:** поля из тикета плюс у модуля `carcass` (false у фасада ПММ) и `note` («корпуса нет, фасад Н6-фасад крепится к посудомойке на объекте»); `title` — полный заголовок «П1 — пенал, 600×2100×560 мм» (у модуля без корпуса «Н6 — фасад посудомоечной машины, 450 мм»); `unit` везде «шт», шаги без номеров (номера ставит PDF). ПРОВЕРИТЬ МАСТЕРУ. (22)
- **Техника в блоке — слова `parts.APPLIANCE_NAMES` для любого вида**, `other` — «другая техника» (модель прибора в сборочный лист не входит; правило КП «модель или ничего» не применяется). (22)
- **Раскладка — `kitchen.assembly_pdf.layout`, `api.assembly_layout`:** строки с кеглем, положением и шириной (общий `TextLine` карты присадки), модуль не разрывается; не помещается и на целую страницу — продолжается с жирной первой строкой «П1, продолжение»; заголовок раздела не остаётся последней строкой страницы; длинные строки переносятся по словам с висячим отступом. Файл вывода — `orders/<заказ>/out/assembly.pdf`. (22)
- **`kitchen production` и `api.PRODUCTION_KINDS`:** список видов выводов, которые пишет `production` (`cutting`, `edging`, `purchase_md`, `purchase_json`, `assembly`); тикет 40 добавит `trip`. Карты присадки в нём нет (решение мастера 2026-11-15): `production` не пишет `drilling-map.pdf` и не вызывает сверку `drilling.reconcile`; команда `kitchen drilling` работает как раньше, файл остался `drilling-map.pdf`. (22)

## Скиллы и харнесс

- **«Наш» симлинк — `kitchen-*`, чья цель лежит внутри `skills/` репозитория.** Только такие `link-skills` переставляет и удаляет; чужие симлинки и настоящие папки не трогает (предупреждение и ненулевой код). `sync-skills` и `link-skills` не пересекаются. (02)
- **Статические проверки скиллов** — логика в `engine/kitchen/skill_lint.py`, запуск `python -m kitchen.skill_lint [папка]` (его зовёт `scripts/check`, код 1 при нарушениях); тесты `tests/test_skill_checks.py` гоняют те же правила на нарушителях из `tests/fixtures/skills_lint/` (по папке на правило; `ok_*` — проходящие), короткие примеры — `tests/test_skill_lint_rules.py`. Проверяются `skills/kitchen-*/SKILL.md`, не `.claude/skills/`. Сообщения вида «скилл: строка N: …». (26)
- **`kitchen.skill_lint` — инструмент, не логика заказов:** в ограждении ADR 0002 он в отдельном наборе `TOOLS` (`tests/test_structure_guards.py`), с тем же эффектом, что `PUBLIC`: тесты вызывают его напрямую. (26)
- **Frontmatter:** ровно `name` и `description`, обе непустые строки; `name` равно имени папки (требование открытого формата, ADR 0003). (26)
- **Команды `kitchen`:** проверяются упоминания внутри кода: обратные кавычки, блоки ``` и ~~~, блоки с отступом в четыре пробела (не пункты списка); строки блока с `\` в конце склеиваются. Вызов — слово `kitchen` не внутри другого слова, пути или имени (`kitchen-brief`, `kitchen.api`, `mykitchen`) и со словом после; одиночный `kitchen` — упоминание программы. Вызов обрывается на `; | & ) ' "`, в строке ищется каждый. Дерево команд и флагов берётся из typer-приложения. Остановки разбора пути (дальше только флаги проверяются): `<…>`, `[…]`, `{…}`, `…`, `...`, слово из заглавных букв (`ЗАКАЗ`), `$…`. Флаг, которого нет у команды и в приложении, — ошибка; `--help` допустим. Группа без подкоманды (в том числе с флагом или заглушкой вместо неё) — ошибка. Проза без кода не проверяется. (26)
- **«Формул нет»** — эвристика по телу `SKILL.md` без frontmatter, правила в `FORMULA_RULES` (одному фрагменту — одно сообщение). «Переменная» — только обозначения размеров: W, H, D, T, L, Ш, В, Г, Т и слова width/height/depth/ширина/высота/глубина/толщина без учёта регистра. Ловится: арифметика с переменной (`W - 4`, `2 * W`, `(W - 4) / 2`), арифметика над числами, если одно из них от трёх цифр или рядом единица длины (`600-4`, `600 + 18`; `3 - 5 вопросов`, `1 / 3`, `24/7`, `2026-047`, даты — нет), словесная (`ширина модуля минус 4`), присваивание формулы размеру (`H = a * b`), число с `мм`, `596x716`, число с десятичной дробью и `см`/`м` (`3,2 м`). **Целое число с `см` или `м` («45 см», «4 м столешницы») не ловится:** такая фраза есть в тексте `kitchen-brief` (пример «посудомойка 45 см»), а скилл правят отдельным тикетом 30. ПРОВЕРИТЬ МАСТЕРУ: нужна ли жёсткость. Ссылки (`references/`) не проверяются. Скилл, которому правило мешает, правят, а не обходят. (26)
- **Набор фраз-триггеров** — `skills/triggers.json`: `{"phrases": [{"text", "skill"}]}`. Нет файла или пустой набор проходит (до тикета 31); при непустом наборе ошибки: повтор (без регистра, ё и лишних пробелов), неизвестный скилл, скилл без фразы, неверная структура или не JSON. Сейчас в наборе три фразы `kitchen-brief`; «не меньше 10» и фразы других скиллов — тикеты 27-29 и 31. (26) Дубль — без учёта регистра, ё, лишних пробелов и знаков в конце. Ноль найденных скиллов, папка `kitchen-*` без `SKILL.md`, нет папки — ошибка. Файл не в UTF-8, BOM, повтор ключа frontmatter, нестроковый ключ — сообщения со строкой, остальные скиллы проверяются дальше. (26)
- **Быстрый опрос в `kitchen-brief`** (решение мастера): третий режим скилла — контакт первым, не больше 5 вопросов, сразу вилка из `quick-estimate`, остальное на звонок и замер. Тикет 44.
- **Холодильник и антресоль** (решение мастера): место отдельностоящего холодильника спрашивается всегда, при верхе до потолка предлагается антресоль; ПММ рядом с мойкой скилл советует сам. Поля и правила — тикет 30, вопросы в интервью — тикет 43.
- **Пустое место в ряду** (`gap`) — одно понятие для отдельностоящей техники и участка без верхних над окном. Антресоль — шаблон `wall_over_fridge` над пустым местом той же ширины. Тикет 32, вставлен перед раскладкой (25). Поля холодильника в схеме брифа (стена, край, `storage.over_fridge`) — тикет 30, решение мастера 2026-11-15; антресоль (38) только читает их.

- **Следующий шаг считает движок** (решение мастера 2026-11-15): «Следующий шаг» в `status` вычисляется по этапу заказа и выводам; «Дальше» — только записи `next` новее последнего `done`. Таблица шагов и поиск заказа по фамилии в косвенном падеже — тикет 49. «Продолжи заказ X» ведёт пятый скилл `kitchen-order` (тикет 31).
- **Схема брифа и правила `check_brief.py`** (тикет 30): разделы `workzone` и `installation` стоят в схеме после `storage`; поля холодильника `wall` и `side` — ключи объекта `appliances.fridge` (подписи `side` — `item_value_labels` у поля), `storage.over_fridge` — обычное enum-поле. Значение не из перечня — запись в `errors` (функция `enum_errors`: enum-поля схемы и ключи объектов вида «enum: a, b»; сравнение по `str`, поэтому `720` и `1.5` числом проходят); так `brief save` такой бриф отклоняет. Элементы списка `appliances.items` (в том числе `who_buys`) не проверяются. Правило места молчит и при пустой `wall` вне раздела холодильника; правило антресоли срабатывает и без раздела холодильника (пустое `built_in` — «не встроенный», как в тикете), а `paths` у него только `storage.over_fridge`, чтобы пустой холодильник не считался закрытым правилом. `kitchen brief save` после записи зовёт `api.status`: пишет `orders/<заказ>/status.md` (с плашкой на моке), перезапись при каждом сохранении, отклонённый бриф файлов не создаёт. Бриф Сергея считается без `wall`/`side`, поэтому находок 12: `fridge_place` и `over_fridge`; вариант с `wall: A, side: left` даёт 11 — оба случая в тестах. (30)
- **Решения мастера 2026-11-15 по ревью тикета 30.** (1) Антресоль над холодильником спрашивается и когда холодильник в брифе не упомянут, а верх до потолка — как сделано. (2) Пол в подписях `installation.floor_evenness` — «ровный / неровный» (стены — «ровные / неровные»): чек-лист выезда печатает «Стены: ровные, пол: ровный». (3) Стена холодильника, которой нет среди `room.walls`, — тот же вопрос `fridge_place` «где холодильник», бриф сохраняется; при пустом `room.walls` сверки нет. (30)

## Верхний угловой по глубине верхних (тикет 50)

- **Решения исполнителя (ПРОВЕРИТЬ МАСТЕРУ):** (1) Смещение верхнего ряда — одна функция `parts.upper_corner_offset`: глубина верхних из мастерской (`верхний.глубина`) плюс толщина фасада именно этого углового модуля (материал фасадов проекта с переопределениями ряда и модуля, как при расчёте деталей). Своя глубина углового модуля (`depth` в проекте) смещения не меняет: мастер сказал «глубина верхних». (2) Нет материала фасада или у него нет толщины — проверка суммы берёт одну глубину верхних, а причину называет `module_build`. (3) `Template.default_depth` убран как неиспользуемый: глубина верхнего углового берётся из ряда, как у всех. (4) Проект Петрова: в конце верхнего ряда стены Б пустое место `ПМ1` 261 мм (1800 − 450 − 750 − 339); модули Петрова не менялись. (5) Эталон `wall_corner_600` пересчитан вручную: боковины 720×320, дно и крыша 568×320 (длинная сторона теперь вдоль стены, передняя кромка на ней же, как у `wall_door_600`), полка 566×300, заглушка и фасад на глубине 320; кромка и фурнитура прежние. (6) Числа Петрова: В4 (глубина 600 → 320) убрала 0,8798 м² ЛДСП (18,111 → 17,2312 м², листов по-прежнему 4, использование 78,1% → 74,3%); число деталей, кромка, фурнитура и присадка не изменились; КП и «пустые места» получили строку «ПМ1». (50)

- **Тесты логики — через `kitchen.api`** (ADR 0002). Тесты, которые уже ходят во внутренние модули, перечислены в `LEGACY_INTERNAL_IMPORTS` (`tests/test_structure_guards.py`); список только сокращается. Значения формул проверяются через `api.parts_from_project` с подменённой формулой; дробная переменная (`H=720.5`) через API недостижима, кейс не переносился. В `test_checks_brief.py` остались `kitchen.brief` и `kitchen.models`: публичной точки для чтения техники из брифа нет. (ревью этапа 1, ретро)
- **Причины записей `LEGACY_INTERNAL_IMPORTS`** (механическая проверка: каждый ключ списка назван в этом файле). `test_brief_api.py`, `test_orders_api.py` — БД заказа через `kitchen.store`; `test_cut_pdf.py`, `test_cut_pdf_dense.py`, `test_pdf.py` — PDF-слой и модель раскроя без заказа; `test_cutting.py` — раскрой на искусственных деталях; `test_row_sum_registry.py`, `test_template_registry.py` — реестр шаблонов `TEMPLATES`. `test_project_cleanup.py` (тикет 45) — `kitchen.common.row_layouts` не сходится только на искусственной стене с меняющейся шириной: через проект такую не собрать. Остальные — в записях своих тем. (45)
- **Эталоны:** в каждом `tests/golden/*.json` первыми идут `_проверить_мастеру` и `_выкладка`; `load_golden` отбрасывает ключи с `_`. ПРОВЕРИТЬ МАСТЕРУ: выкладки в эталонах. (ревью этапа 1)
- **Фикстура Петрова** (`tests/fixtures/petrov_project.json`): П1 в нижнем ряду стены A, Н4/В4 с `adjacent_wall: Б`, духовка и СВЧ в П1 с габаритами корпуса и `niche_*`, варочная в Н1, ПММ в Н6, мойка в Н5 (`without_back: true`, `contents.inserts: [bin_2sec]`), вытяжка в В1 с габаритами и `niche_*`, сушка в В5 и вытяжка В1 с подъёмником `aventos_hks`; цвета RAL 7044 и RAL 9003.
